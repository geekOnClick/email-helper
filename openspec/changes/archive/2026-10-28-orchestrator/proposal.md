# Proposal

## Why

Фаза 2 начата: готов `RouterAiClient` (change `llm-client`, один шаг запрос→ответ с `tool_calls`) и реестр тулов `mail.*` (Фаза 1). Но «мозга» ещё нет — никто не крутит цикл `модель → tool_calls → вызов тулов → role:"tool" → модель`, не помнит реплики диалога и не умеет делегировать задачи субагентам. Без этого каркаса невозможны ни `mail.analyze` (анализатор), ни векторный поиск (Фаза 3), ни CLI (Фаза 5): все они опираются на оркестратор, который разбирает интент пользователя и ведёт его к результату через tool-calling. Этот change вводит ядро агентной оркестрации — следующий шаг Фазы 2 после `llm-client`.

## What Changes

- **Цикл tool-calling** как переиспользуемый движок `runToolLoop` (в `src/agents/loop.ts`): принимает готовые сообщения, mapped-тулы и resolver; итерирует `client.chat()` → исполняет `tool_calls` через resolver → добавляет `role:"tool"` результаты → повторяет, пока модель не даст финальный текст без вызовов. Не зависит от роли/системного промпта — чистый механизм-loop.
- **Защита от зацикливания**: лимит итераций (`AGENT_MAX_ITERATIONS`, default 10); при исчерпании — контролируемая остановка с последним ответом и признаком усечения.
- **Подача ошибок тулов обратно модели**: тул, бросивший исключение, неизвестный тул и невалидные аргументы НЕ роняют цикл — их результат уходит как `role:"tool"` с описанием ошибки, чтобы модель могла отреагировать.
- **Сериализация и ограничение результатов тулов**: результат тулa сериализуется в строку для `role:"tool"`; результат длиннее `AGENT_MAX_TOOL_RESULT_CHARS` (default 20000) усекается с маркером (чтобы большие тела писем из `mail.fetch` не раздували контекст).
- **Класс `Orchestrator`** (в `src/agents/orchestrator.ts`): фасад над loop для роли `orchestrator` — грузит системный промпт из `skills/orchestrator.md`, строит список tools из реестра (`mapToolsToOpenAi(listTools())`), держит контекст диалога (история `ChatMessage[]` между репликами), принимает запрос пользователя, прогоняет loop, возвращает итоговый ответ + метаданные.
- **Seam делегирования субагентам**: интерфейс `Subagent` (`{ name, description, run(input) }`) + `SubagentRegistry`; тул `delegate` (`{ subagent, instruction }`) в наборе тулов оркестратора — вызывает зарегистрированного субагента. Сами реализации субагентов (`analyzer`, `helper`) — отдельные change'ы (`analyzer-agent`, `helper-agent`); здесь только контракт и регистрация (тестируется стаб-субагентом). Пока субагенты не зарегистрированы, оркестратор функционален, вызывая `mail.*` напрямую.
- **Загрузчик скилов** `loadSkill(name)` (в `src/agents/skill-loader.ts`) — чтение `skills/*.md` (для оркестратора; переиспользуется будущими агентами).
- **Наполнение `skills/orchestrator.md`** (вместо каркаса-заглушки) — системный промпт роли оркестратора: роль, доступные тулы, формат плана/ответа, ограничения (не отправлять без подтверждения, не угадывать учётные данные).
- **Конфиг**: +2 опц. поля (`AGENT_MAX_ITERATIONS`, `AGENT_MAX_TOOL_RESULT_CHARS`).
- **Юнит-тесты** с моком `RouterAiClient` (фикстуры ответов: текст-финал, один tool_call → результат → финал, несколько вызовов подряд, ошибка тулa, неизвестный тул, невалидные args, исчерпание итераций); тест делегирования со стаб-субагентом; тест контекста диалога (две реплики, вторая помнит первую).

## Capabilities

### New Capabilities

- `agent/orchestrator`: каркас оркестратора агента — цикл tool-calling (модель → tool_calls → вызов тулов из реестра → role:"tool" ответ → повтор), контекст диалога, загрузка системного промпта роли по файлу-скилу, seam делегирования субагентам (интерфейс + реестр + тул `delegate`) с защитой от зацикливания и подачей ошибок тулов обратно модели.

### Modified Capabilities

Нет — `llm/routerai` (клиент) используется как есть, его требования не меняются; тулы `mail/connection`, `mail/search`, `mail/attachments` вызываются из цикла, но их спеки поведения не затрагиваются. Субагенты `agent/analyzer` и `agent/helper` — отдельные change'ы со своими спеками.

## Impact

- **Новый код:** `src/agents/loop.ts` (`runToolLoop`, `ToolLoopOptions`, `ToolLoopResult`, сериализатор/тruncator результатов), `src/agents/orchestrator.ts` (`Orchestrator`), `src/agents/subagent.ts` (`Subagent`, `SubagentRegistry`, тул `delegate`), `src/agents/skill-loader.ts` (`loadSkill`), `src/agents/index.ts` (экспорт вместо заглушки).
- **Без новых runtime-зависимостей** — `RouterAiClient`, `mapToolsToOpenAi`, реестр тулов уже готовы; `node:fs`/`node:path` — встроенные.
- **Конфиг:** +2 опц. поля в `ConfigSchema` (`AGENT_MAX_ITERATIONS` default `10`, `AGENT_MAX_TOOL_RESULT_CHARS` default `20000`) — обратно-совместимо.
- **Системный промпт:** `skills/orchestrator.md` наполняется (был каркас); `skills/analyzer.md`, `skills/helper.md` — без изменений (свои change'ы).
- **Внешние системы:** только через тулы реестра (IMAP-провайдеры) и `RouterAiClient` (`/chat/completions`) — новых эндпоинтов нет.
- **Тесты:** мок `RouterAiClient` (injectable-transport из `llm-client`), стаб-субагент; на gated-интеграцию (`INTEGRATION_LLM=1`) против живого RouterAI не опираемся (сервис временно 500 — см. observation в `archive/2026-10-28-llm-client/design.md`), но оставляем помеченный gated-тест цикла оркестрации, который заработает при восстановлении API.
- **Не затрагивает:** реализации субагентов (отдельные change'ы), `mail.analyze`, векторную БД (Фаза 3), отправку (Фаза 4), транспорты (Фазы 5–7).
- **Новые спеки:** `agent/orchestrator` (new capability).
