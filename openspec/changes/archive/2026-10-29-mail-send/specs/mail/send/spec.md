# Spec Delta

## Purpose

Отправка писем по SMTP (Яндекс basic, Outlook OAuth2 XOAUTH2) по строгим критериям письма с поддержкой нескольких получателей (TO/CC/BCC), вложений и обязательным подтверждением перед отправкой.

## ADDED Requirements

### Requirement: Отправка письма по SMTP

Система SHALL предоставлять тул отправки письма, который по логину аккаунта и критериям письма (получатели TO/CC/BCC, тема, тело, опциональные вложения, кодировка) отправляет письмо через SMTP-сервер провайдера, используя учётные данные аккаунта, и возвращает идентификатор отправленного письма и список фактических получателей.

#### Scenario: Успешная отправка письма с одним получателем

- **WHEN** тул отправки вызывается с логином, критериями письма (один TO, тема, тело) и подтверждением
- **THEN** система отправляет письмо через SMTP и возвращает идентификатор письма и список получателей

#### Scenario: Отправка с несколькими получателями (TO/CC/BCC)

- **WHEN** тул отправки вызывается с получателями в полях TO, CC и BCC
- **THEN** система отправляет одно письмо всем указанным получателям и возвращает объединённый список получателей

#### Scenario: Отправка с вложениями

- **WHEN** тул отправки вызывается с путями к локальным файлам-вложениям
- **THEN** система прикрепляет файлы к письму и отправляет письмо с вложениями

#### Scenario: Требуется активное подключение

- **WHEN** тул отправки вызывается с логином без установленного подключения к ящику
- **THEN** система возвращает ошибку с указанием, что требуется предварительно подключиться

#### Scenario: Ошибка SMTP

- **WHEN** SMTP-сервер отклоняет отправку (недоступен, превышен лимит, отклонён адрес)
- **THEN** система возвращает ошибку отправки с понятным сообщением, не раскрывая секрет учётных данных

### Requirement: Подтверждение перед отправкой

Система SHALL NOT отправлять письмо, пока пользователь явно не подтвердит отправку. Без подтверждения система SHALL возвращать предпросмотр черновика с валидацией критериев и SHALL NOT устанавливать SMTP-соединение и не отправлять письмо.

#### Scenario: Предпросмотр без подтверждения

- **WHEN** тул отправки вызывается с критериями письма и без подтверждения (confirm не равно true)
- **THEN** система валидирует критерии, возвращает предпросмотр черновика и признак готовности false, не отправляя письмо

#### Scenario: Подтверждение инициирует отправку

- **WHEN** тул отправки вызывается с подтверждением (confirm равно true)
- **THEN** система валидирует критерии и отправляет письмо, возвращая идентификатор и признак готовности true

#### Scenario: Некорректные критерии при подтверждении

- **WHEN** тул отправки вызывается с подтверждением, но критерии невалидны (нет получателей, пустая тема)
- **THEN** система SHALL NOT отправлять письмо и возвращает ошибки валидации с признаком готовности false

### Requirement: Строгие критерии письма

Система SHALL принимать критерии письма, включающие получателей (TO, опционально CC, опционально BCC как адреса email с опциональным именем), тему, текстовое тело, опциональную HTML-альтернативу тела, опциональные вложения (пути к локальным файлам) и кодировку (по умолчанию UTF-8), и SHALL валидировать их перед отправкой.

#### Scenario: Минимальный набор критериев

- **WHEN** тул вызывается с хотя бы одним получателем TO, темой и текстовым телом
- **THEN** система принимает критерии как валидные

#### Scenario: Отсутствие получателей

- **WHEN** тул вызывается без получателей во всех полях (TO, CC, BCC пусты)
- **THEN** система возвращает ошибку валидации, требующую хотя бы одного получателя

#### Scenario: Некорректный адрес получателя

- **WHEN** тул вызывается с адресом, не соответствующим формату email
- **THEN** система возвращает ошибку валидации с указанием некорректного адреса

#### Scenario: Пустая тема

- **WHEN** тул вызывается с пустой или отсутствующей темой
- **THEN** система возвращает ошибку валидации, требующую тему письма

### Requirement: SMTP-аутентификация по провайдеру

Система SHALL аутентифицироваться на SMTP-сервере провайдера, используя ту же стратегию учётных данных, что и для IMAP: для Яндекс — логин и пароль приложения (`basic`); для Outlook — access token через механизм XOAUTH2 (`oauth2`), полученный и обновляемый через то же хранилище OAuth2-токенов, что и IMAP.

#### Scenario: Яндекс SMTP basic

- **WHEN** отправляется письмо с Яндекс-аккаунта (стратегия basic)
- **THEN** система аутентифицируется на `smtp.yandex.ru` логином и паролем приложения

#### Scenario: Outlook SMTP OAuth2

- **WHEN** отправляется письмо с Outlook-аккаунта (стратегия oauth2)
- **THEN** система аутентифицируется на SMTP-сервере Outlook access token через XOAUTH2, переиспользуя refresh token из хранилища

#### Scenario: SMTP-сессия независима от IMAP-сессии

- **WHEN** отправляется письмо при активной IMAP-сессии
- **THEN** система использует отдельное SMTP-соединение и не нарушает активную IMAP-сессию

### Requirement: Безопасное хранение учётных данных при отправке

Система SHALL NOT принимать учётные данные (пароль, access token) в аргументах тулa отправки и SHALL NOT логировать секреты или выводить их в сообщения об ошибках. Учётные данные SHALL извлекаться из конфигурации аккаунта и хранилища токенов по логину.

#### Scenario: Секреты не в аргументах тулa

- **WHEN** тул отправки вызывается с логином и критериями письма
- **THEN** аргументы тулa не содержат пароля, access token или refresh token

#### Scenario: Секреты не попадают в логи

- **WHEN** происходит ошибка SMTP-аутентификации или отправки
- **THEN** сообщение об ошибке не содержит пароля, access token или refresh token
