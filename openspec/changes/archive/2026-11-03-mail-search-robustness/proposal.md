# Proposal: mail-search-robustness

## Why

Тул `mail.search`, вызываемый внешними агентами по MCP, зависает на ~час и/или падает с `Connection not available` на ящиках с большим числом писем (подтверждено на Яндекс-ящике счетов коммунальных услуг, INBOX = 23 260 писем). Причина: когда серверный IMAP SEARCH Яндекса по длинным кириллическим темам с литералами (месяц+год, кавычки, «ё») возвращает `0` (хотя письмо существует), включается неограниченный client-side фолбэкк `fetchAll('1:*')` по всем письмам папки. На 23 тыс. писем это занимает ~час, а после больших выборок соединение Яндекса обрывается, и последующие поиски тоже падают. Внешний агент тратит все попытки на зависший поиск и не доходит до надёжных критериев (`from`/`since`), которые сервер Яндекса обрабатывает корректно. Сейчас MCP-вызовы `mail.search` не логируются (`noopToolLogger` в MCP-пути), что делает невозможным диагностику «почему не нашёл».

## What Changes

- **Ограниченный client-side фолбэкк (search).** Система SHALL NOT выполнять `fetchAll('1:*')` по всей папке. Вместо этого при ненадёжном серверном поиске по тексту (`subject`/`from`/`to`) система SHALL сузить выборку надёжными серверными критериями (`since`/`before`/`from`/`to`/флаги), которые присутствуют в запросе, и фетчить метаданные только по суженному UID-набору. Если надёжных критериев нет (запрос содержит только `subject`) — система SHALL применить серверный `SINCE` по умолчанию (последние ~180 дней, `MAIL_SEARCH_FALLBACK_DAYS`, по умолчанию 180), чтобы не фетчить весь ящик.
- **Повторная дофильтровка серверного результата (search).** Система SHALL ALWAYS применять локальную фильтрацию (`matchesCriteria`) к метаданным, полученным серверным поиском, — не только при пустом серверном ответе. Это устраняет ложный непустой набор, когда Яндекс применяет только часть текстовых критериев (например, `SINCE`, а кириллический `SUBJECT`-литерал «съедается»).
- **Таймаут IMAP-операций.** Система SHALL ограничивать длительность одного вызова тулов, работающих по IMAP (`mail.search`, `mail.fetch`, `mail.downloadAttachments`, `mail.listFolders`), таймаутом `MAIL_OP_TIMEOUT_MS` (по умолчанию 30000 мс). При превышении — ошибка с понятным сообщением, без висящего вызова. Для `mail.search` таймаут покрывает совокупность серверного поиска, фолбэкка и fetch'а метаданных в рамках одной попытки (до учёта повторов).
- **Повтор с переподключением при обрыве соединения.** При обрыве IMAP-соединения во время операции (`Connection not available` и аналогичные сетевые ошибки) система SHALL переподключить IMAP-сессию и повторить операцию до `MAIL_OP_MAX_RETRIES` раз (по умолчанию 1). Применяется ко всем IMAP-операциям тулов: `mail.search`, `mail.fetch`, `mail.downloadAttachments`, `mail.listFolders`. Это устраняет каскадный падёж последующих операций после большой выборки и обрыва соединения у Яндекса. Переподключение реализовано через существующий lifecycle провайдера (dispose + connect) — без изменения capability `mail/connection`.
- **Без изменений контракта тулов.** `inputSchema` тулов и возвращаемые типы (`SearchResult`, `EmailFull`, `DownloadResult`, `Folder[]`) не меняются; для `mail.search` `limit`/`offset`/`hasMore`/`total` работают как раньше. Pagination по `offset` поверх UID-набора сохраняется: большой суженный UID-набор не тащит все метаданные разом — фетч метаданных идёт только по `slice` (`offset..offset+limit`).
- **Не затрагивается**: критерии поиска, формат `EmailMessage`, тул `mail.send` (SMTP-путь отдельный), OAuth2, динамические креды `mail.connect` (change `mcp-dynamic-credentials`), agent-loop.

## Capabilities

### Modified Capabilities

- **`mail/search`** — ограничение client-side фолбэкка (без `fetchAll('1:*')`, сужение надёжными критериями + `SINCE` по умолчанию), обязательная дофильтровка серверного результата, таймаут операции (`MAIL_OP_TIMEOUT_MS`), повтор с переподключением (`MAIL_OP_MAX_RETRIES`).
- **`mail/attachments`** — таймаут операции (`MAIL_OP_TIMEOUT_MS`) и повтор с переподключением (`MAIL_OP_MAX_RETRIES`) для `mail.fetch` и `mail.downloadAttachments` (а также `mail.listFolders`, т.к. использует ту же IMAP-сессию).

### New Capabilities

(нет — все изменения в существующей capability `mail/search`)

## Impact

- **Код**: `src/tools/mail/providers/abstract-imap-provider.ts` (методы `search`, `fetch`, `downloadAttachments`, `listFolders`; `clientSideSearch`, `matchesCriteria`, новая логика сужения/таймаута/повтора; общий helper `isConnectionError` и обёртка операции таймаутом+retry), `src/tools/mail/mail-search.tool.ts` (без изменений схемы), `src/config` (чтение `MAIL_OP_TIMEOUT_MS`/`MAIL_OP_MAX_RETRIES`/`MAIL_SEARCH_FALLBACK_DAYS`).
- **Тесты**: unit-тесты для `AbstractImapProvider.search`: (1) серверный поиск по `subject` вернул `0` → фолбэкк сужается `SINCE` по умолчанию, `fetchAll` только по суженному диапазону, не `1:*`; (2) серверный поиск вернул непустой набор, не совпадающий по `subject` локально → дофильтровка отсекает лишние; (3) таймаут → ошибка, без зависания; (4) `Connection not available` → reconnect + retry до `MAIL_OP_MAX_RETRIES`, успех на повторе; (5) превышен `MAX_RETRIES` → ошибка. Unit-тесты для `downloadAttachments`/`fetch`/`listFolders`: таймаут → ошибка; `Connection not available` → reconnect + retry, успех на повторе; успех без обрыва — без переподключения.
- **Конфигурация**: `.env` получает три новые переменные (`MAIL_OP_TIMEOUT_MS`, `MAIL_OP_MAX_RETRIES`, `MAIL_SEARCH_FALLBACK_DAYS`) с дефолтами; `.env.example` документирует их.
- **MCP**: автоматически — поведение `mail.search`/`mail.fetch`/`mail.downloadAttachments` становится надёжным для внешних агентов (без зависания и каскадного падежа соединения).
- **Обратная совместимость**: существующие вызовы тулов работают; новые env-переменные опциональны (дефолты). Единственное видимое поведение-изменение — операции, ранее зависавшие/падавшие каскадом из-за обрыва, теперь либо быстро возвращают результат, либо ошибку по таймауту, либо успешно ретраятся с переподключением.
