# Spec Delta

## ADDED Requirements

### Requirement: Ограничение client-side фолбэкка

Когда серверный IMAP SEARCH по текстовому критерию (`subject`, `from`, `to`) возвращает пустой результат, система MAY выполнить client-side фолбэкк (fetch метаданных и локальную фильтрацию), но SHALL NOT fetch'ить всю папку (`1:*`). Фолбэкк SHALL сужать диапазон fetch'а надёжными серверными критериями из запроса, а при их отсутствии — `SINCE` по умолчанию.

#### Scenario: Фолбэкк сужается имеющимся критерием since

- **WHEN** серверный поиск по `subject` вернул `0`, а в запросе задан `since`
- **THEN** client-side фолбэкк fetch'ит метаданные только писем с `internalDate >= since` (серверный `SINCE`), а не всей папки, и фильтрует их локально по `subject`

#### Scenario: Фолбэкк сужается имеющимся критерием from

- **WHEN** серверный поиск по `subject` вернул `0`, а в запросе задан `from`
- **THEN** client-side фолбэкк выполняет серверный поиск по `from`, fetch'ит метаданные только по найденным UID'ам и фильтрует их локально по `subject`, не обращаясь к `1:*`

#### Scenario: Фолбэкк при запросе только subject — SINCE по умолчанию

- **WHEN** серверный поиск по `subject` вернул `0`, и в запросе нет `since`/`before`/`from`/`to`/флагов
- **THEN** client-side фолбэкк применяет серверный `SINCE` = последние `MAIL_SEARCH_FALLBACK_DAYS` дней (по умолчанию 180) и fetch'ит метаданные только в этом диапазоне, не по всей папке

#### Scenario: Фолбэкк не обращается ко всей папке

- **WHEN** срабатывает client-side фолбэкк при любом сочетании критериев
- **THEN** система не выполняет `fetchAll('1:*')` по всей папке; диапазон fetch'а всегда сужен надёжными критериями или `SINCE` по умолчанию

### Requirement: Дофильтровка серверного результата

Система SHALL ALWAYS применять локальную фильтрацию по всем текстовым критериям (`subject`, `from`, `to`) и критериям даты (`since`, `before`) к метаданным, полученным серверным поиском, — не только при пустом серверном ответе. Это гарантирует, что ненадёжный серверный поиск (когда IMAP-сервер применяет только часть текстовых критериев, например только `SINCE`, а кириллический `SUBJECT`-литерал игнорирует) не вернёт ложный непустой набор, не соответствующий теме.

#### Scenario: Ложные совпадения сервера отсекаются локально

- **WHEN** серверный поиск по `subject` + `since` вернул письма, тема которых не содержит заданную подстроку (сервер применил только `SINCE`)
- **THEN** система дофильтровывает результат локально и не возвращает письма, не соответствующие `subject`

#### Scenario: Точные совпадения сохраняются

- **WHEN** серверный поиск по `subject` вернул письма, действительно содержащие подстроку в теме
- **THEN** система возвращает их после локальной дофильтровки (поведение поиска по теме не ухудшается)

### Requirement: Таймаут операции поиска

Система SHALL ограничивать длительность одного вызова `mail.search` таймаутом `MAIL_OP_TIMEOUT_MS` (по умолчанию 30000 мс). При превышении система SHALL прервать операцию и вернуть ошибку с понятным сообщением, не оставляя висящий вызов. Таймаут применяется к совокупности серверного поиска, фолбэкка и fetch'а метаданных в рамках одной попытки (до учёта повторов).

#### Scenario: Поиск прерывается по таймауту

- **WHEN** операция поиска не укладывается в `MAIL_OP_TIMEOUT_MS` (например, серверный поиск или фолбэкк затягиваются)
- **THEN** система прерывает операцию и возвращает ошибку, сообщающую о превышении таймаута, без зависания вызова

#### Scenario: Быстрый поиск не обрывается

- **WHEN** операция поиска укладывается в `MAIL_OP_TIMEOUT_MS`
- **THEN** система возвращает нормальный результат, таймаут не срабатывает

### Requirement: Повтор операции поиска при обрыве соединения

При обрыве IMAP-соединения во время поиска (ошибки вида `Connection not available` и иные сетевые сбои) система SHALL переподключить IMAP-сессию и повторить поиск, до `MAIL_OP_MAX_RETRIES` повторов (по умолчанию 1). Переподключение SHALL использовать существующий lifecycle провайдера (закрытие старой сессии и новое подключение) без изменения учётных данных аккаунта. Если все повторные попытки исчерпаны и соединение не восстановлено — система SHALL вернуть ошибку, маскирующую секреты.

#### Scenario: Обрыв соединения — повтор с переподключением

- **WHEN** во время поиска IMAP-соединение обрывается (`Connection not available`)
- **THEN** система переподключает сессию и повторяет поиск; при успехе на повторе возвращает нормальный результат

#### Scenario: Успех на первой попытке — без повторов

- **WHEN** поиск завершается успешно без обрыва соединения
- **THEN** система не выполняет переподключение и лишние повторы, возвращает результат сразу

#### Scenario: Исчерпание повторов — ошибка

- **WHEN** обрыв соединения повторяется чаще `MAIL_OP_MAX_RETRIES`
- **THEN** система возвращает ошибку, сообщающую о недоступности соединения, с замаскированными секретами

#### Scenario: Секреты маскируются в ошибке повтора

- **WHEN** повтор с переподключением завершается ошибкой аутентификации или соединения
- **THEN** сообщение об ошибке не содержит пароля приложения, логина в открытом виде или access token
