# Design

## Context

Проект — ESM TypeScript-приложение (`type: module`, tsx-runtime). Текущая
архитектура имеет два транспорта: CLI REPL (`src/transport/cli/`) и MCP-сервер
(`src/mcp/`). Оба собираются из общего ядра через `bootstrap()` — он грузит
конфиг/аккаунты, строит `RouterAiClient`, агентов (`orchestrator`, `analyzer`),
регистрирует mail-тулы. Тулов-реестр статичен (`registerTool`), MCP-путь уже
имеет HTTP-сервер на `node:http` (`src/mcp/http.ts`, stateless, `/mcp`).

CLI-команды (`/smart-search`, `/analyze`, `/smart-send`, ...) построены на
**синхронном пошаговом диалоге** через `ConsoleIO.readline()` — они спрашивают
пользователя по очереди и пишут результат через `write`. Это жёстко привязывает
логику к терминалу и блокирует переиспользование в вебе.

Конфигурация — `.env` (переменные + `ACCOUNTS` JSON), `Config` из `schema.ts`.
Аккаунты — `MailAccount` (provider/login/password/authStrategy), реестр
`AccountRegistry` (in-memory, источник правды для тулов). Пароли извлекаются
бэкендом по `login`+`provider` (MCP-тул `mail.connect` не принимает пароль).

## Goals / Non-Goals

**Goals:**
- Веб-альтернатива CLI с макетом почтового клиента и читаемым рендером
- Переиспользование ядра (тулы, агенты, LLM-клиенты) без дублирования
- CLI сохраняет текущее поведение; рефакторинг команд не ломает существующие тесты
- localhost-only (безопасность, как MCP HTTP)
- Один процесс на CLI+веб (`npm start` → REPL, `npm run web` → HTTP-сервер)

**Non-Goals:**
- Удаление CLI — веб аддитивен
- Реальный многопользовательский доступ/аутентификация (localhost-only, один
  пользователь, как CLI)
- Замена MCP-транспорта — веб использует REST над тулами, MCP остаётся
- Push-обновления (WebSocket) — первой версии достаточно polling/запрос-ответ
- Мобильная адаптация — desktop-first (читаемый макет почтового клиента)

## Decisions

### D1: Выделение чистых доменных функций команд (core-слой)

**Решение:** каждая команда (`smart-search`, `analyze`, `smart-send`, ...)
рефакторится в две части:
- **`run<Cmd>(deps)`** в новом `src/transport/commands/` — чистая доменная
  функция, принимает DTO (без `ConsoleIO`), вызывает тулы/агентов, возвращает
  структурированный результат.
- **CLI-обработчик** в `src/transport/cli/commands/` — тонкий адаптер: собирает
  ввод через `ConsoleIO.readline()`, вызывает чистую функцию, рендерит результат
  через `write`.

**Альтернативы:** (а) дублировать логику в вебе — отброшено (расхождение
поведений); (б) эмулировать `ConsoleIO` в вебе через async-очередь — отброшено
(пошаговый диалог плохо мапится на формы, ломает UX).

**Обоснование:** CLI и веб разделяют общую логику, но разные UX. Чистые функции
дают переиспользование + тестируемость без IO; CLI-адаптер сохраняет текущее
поведение REPL (существующие тесты `cli-commands-*.test.ts` продолжают работать,
т.к. адаптер обёртывает ту же логику).

### D2: Встроенный Node HTTP-сервер (без Express/Fastify)

**Решение:** бэкенд веба — `src/transport/web/server.ts` на встроенном
`node:http`, как существующий `src/mcp/http.ts`. Роутинг — простой
маппинг `method + url → handler` (без фреймворка). `bootstrap()` переиспользуется.

**Альтернативы:** (а) Express/Fastify — отброшено (лишняя зависимость, проект
уже использует `node:http` для MCP, объём эндпоинтов мал); (б) отдельный процесс
— отброшено (пользователь хочет один `npm start` для CLI+веб).

**Обоснование:** консистентность с MCP-транспортом, минимум зависимостей,
переиспользование `bootstrap()`. Роутинг ~10 эндпоинтов тривиален для ручного
маппинга.

### D3: React + Vite + Material-UI, сборка в `dist/client/`

**Решение:** фронтенд — SPA в `src/transport/web/client/` (React 18, Vite,
`@vitejs/plugin-react`, Material-UI). Vite-сборка → `dist/client/`, Node-сервер
отдаёт статику с корня (`/`). Dev-режим (`web:dev`) — Vite dev-сервер (порт
5173) + API на `WEB_PORT`, CORS разрешает dev-origin.

**Альтернативы:** (а) Next.js — отброшено (SSR/SSG избыточны для localhost-SPA,
лишний слой сборки); (б) plain CSS — отброшено (пользователь выбрал Material-UI).

**Обоснование:** Vite — стандарт для React-SPA, быстрая dev-сборка, простая
интеграция статической выдачи с Node-сервером. Material-UI даёт готовые
компоненты (AppBar, List, Drawer, Card) для макета почтового клиента.

### D4: Макет почтового клиента — AppBar + Drawer + правая панель

**Решение:** макет Material-UI:
- **AppBar сверху** — тулбар команд (кнопки/меню: Smart Search, Analyze, ...,
  Add Account) + дропдаун аккаунта.
- **Drawer/List слева** — список писем (тема, отправитель, дата, флаг
  непрочитанного).
- **основная зона справа** — чтение тела письма / отчёт анализа / форма (по
  выбранной команде). Занимает большую часть ширины (`flex: 1`).

**Альтернативы:** (а) чат-подобный wizard — отброшено (пользователь выбрал
формы); (б) вкладки — отброшено (одновременно видны список и чтение удобнее).

**Обоснование:** канонический почтовый UX (список + чтение), правая панель —
основная зона как просил пользователь, тулбар сверху для быстрого доступа к
командам.

### D5: DTO и JSON-контракты API

**Решение:** DTO для каждого эндпоинта — типизированные интерфейсы в
`src/transport/web/api/dtos.ts`. Ответы — JSON: успех → доменный объект
(`EmailMessage`, `EmailFull`, `SearchResult`, ...), ошибка →
`{ error: string, code?: string }`. HTTP-коды: 200/201 успех, 404 аккаунт не
найден, 400 невалидный DTO, 500 внутренняя ошибка.

**Обоснование:** чистые контракты, переиспользование доменных типов (уже
сериализуемы — `EmailMessage` это plain object), единая форма ошибок.

### D6: Режим запуска (`--web` флаг)

**Решение:** `src/index.ts` расширяется разбором `--web` → если установлен,
запускается веб-сервер (`runWeb()`) вместо REPL. Скрипты `package.json`:
- `web` → `tsx src/index.ts --web` (прод-режим: отдаёт собранное SPA)
- `web:dev` → concurrently Vite dev + `tsx src/index.ts --web` (dev-режим)
- `web:build` → `vite build` (сборка SPA в `dist/client/`)

**Альтернативы:** отдельный entrypoint `src/web.ts` — отброшено (дублирование
bootstrap-логики; флаг в существующем `index.ts` проще).

**Обоснование:** один entrypoint, общая bootstrap-инициализация, режим
переключается флагом.

### D7: Чтение тела письма — новый эндпоинт (не новая команда CLI)

**Решение:** чтение тела письма (`GET /api/emails/:login/:uid`) вызывает
существующий тул `mail.fetch` напрямую. В CLI отдельной команды нет (тело
открывается через `/smart-search` или `/analyze`); в вебе это отдельная
операция, т.к. макет почтового клиента требует показа тела по клику.

**Обоснование:** переиспользование готового тула, без новой доменной логики.

## Risks / Trade-offs

- **Рефакторинг команд меняет стабильный код.** Существующие CLI-тесты
  (`cli-commands-*.test.ts`) — сетка безопасности: адаптер обёртывает ту же
  логику, контракт сохраняется, тесты продолжают проходить. Риск: пропустить
  поведенческое расхождение → митигируется сохранением всех сценариев в delta-спеке.
- **Размер зависимостей.** React + MUI + Vite добавят ~мегабайты в
  `node_modules` и `dist/`. Принимается: веб-альтернатива того стоит, сборка
  изолирована в `dist/client/`, не влияет на CLI/MCP.
- **Синхронность mail-операций в HTTP.** Команды (особенно `/analyze-many` с
  LLM-анализом) могут выполняться 10-60с. HTTP-запрос блокируется до результата.
  Первая версия — без WebSocket/стриминга; фронтенд показывает индикатор
  прогресса (`CircularProgress`). Риск: таймаут прокси/браузера — митигируется
  localhost (нет прокси) и разумными таймаутами LLM (`.env` уже настроен:
  `LLM_REQUEST_TIMEOUT_MS=30000`, `LLM_RETRIES=1`).
- **Пароль в `POST /api/accounts`** передаётся в теле HTTP. Безопасно только при
  localhost-only (`127.0.0.1`). Принимается (как CLI вводит пароль в stdin);
  `WEB_HOST=127.0.0.1` по умолчанию, и спека требует не возвращать пароль.
- **Без push-обновлений.** Новый аккаунт, добавленный в вебе, виден в CLI только
  после перезапуска (реестр in-memory общий через `bootstrap()`, но CLI-процесс
  отдельный). Первая версия: оба транспорта в одном процессе (`--web`) не
  запускают REPL одновременно — приемлемо.
