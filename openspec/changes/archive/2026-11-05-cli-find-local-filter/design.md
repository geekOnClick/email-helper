# Design

## Context

Тул `mail.search` (спека `mail/search`) и его bounded fallback (change `mail-search-robustness`)
спроектированы так, что при пустом серверном результате по текстовому критерию сужают fetch
надёжными критериями из запроса (`since`/`before`/`from`/`to`/флаги). Проблема: `from` помечен
как «надёжный» в `buildNarrowedQuery`, но на Яндекс-сервере IMAP SEARCH по `FROM` для некоторых
адресов (напр. `no-reply@igm.gg`) возвращает 0 даже при существующих письмах. Если `/find`
передаёт `subject` + `from` без `since`, серверный поиск по ним даёт 0, fallback сужается по
`from` → снова 0 → «Ничего не найдено». Письмо при этом есть в INBOX и находится через
`subject` + надёжный `since`.

Команда `/find-all` (change `cli-find-all-command`, design D1) уже решила эту же проблему: на
сервер идут **только даты** (`since`/`before`), тема/отправитель фильтруются локально через
`collectAllMessages` с пагинацией. `/find` пока использует прямой серверный поиск по всем
критериям и потому уязвим к ненадёжности серверного SEARCH.

См. `proposal.md` — таблица воспроизведения на реальном ящике.

## Goals / Non-Goals

**Goals:**

- `/find` находит письма по теме и/или отправителю (с опц. датой), которые серверный SEARCH
  Яндекса по теме/отправителю пропускает.
- Переиспользовать проверенную машину `/find-all` (`collectAllMessages`) — без дублирования
  логики пагинации/локальной фильтрации.
- Не менять тулы `mail.search`/провайдеры и спеку `mail/search` — MCP-путь сохраняется.

**Non-Goals:**

- Не меняем тулы и спеку `mail/search` — bounded fallback тула остаётся как есть (он защищает
  `/find`-без-дат и MCP-вызовы; ответственность `/find` — свой собственный подход «даты на
  сервер, тема/отправитель локально»).
- Не меняем мастер ввода `/find` (`promptSearchCriteria`: тема/дата/отправитель) и формат
  вывода (`formatMessageList`: тема, отправитель, дата, UID).
- Не вводим диапазон дат в `/find` (одно поле `дата`) — для диапазона есть `/find-all`.

## Decisions

### D1: На сервер — только даты; тема/отправитель — локальный фильтр (как /find-all)

`/find` переходит на тот же подход, что `/find-all`: `buildSearchArgs` формирует
`FindAllSearchArgs { serverCriteria: { since, before? }, subject?, from? }`, где
`serverCriteria` содержит **только** даты. Поиск выполняется через `collectAllMessages` (из
`find-all.ts`), который пагинирует `mail.search` по `since`/`before`/`limit`/`offset` и
фильтрует результат локально по `subject`/`from` (case-insensitive, нормализация пробелов —
уже реализовано в `collectAllMessages`/`matchesLocalFilters`).

- **Почему не чинить `buildNarrowedQuery` в тулe:** это меняет спеку `mail/search` и рискует
  регрессией `/find`-без-дат и MCP-клиентов. Команда `/find-all` уже доказала, что подход
  «даты на сервер, тема локально» работает без изменений тула. Отклонено.
- **Почему `from` тоже локально, а не на сервер:** серверный SEARCH Яндекса по `FROM` для ряда
  адресов ненадёжен (воспроизведено: `from=no-reply@igm.gg` → 0 при существующем письме).
  Локальная фильтрация по `from` (подстрока в адресе/имени) надёжна.

### D2: Семантика `дата` — один день включительно

Поле `дата` мастера `/find` — конкретный день, не диапазон. Серверу передаётся `since` =
полночь указанного дня и `before` = полночь следующего дня (включительно), как `дата по` в
`/find-all` (там `before = dateTo + 1 день`). Дата строится как локальная полночь через
`isoToDate` (`new Date(year, month-1, day)`) — уже экспортируется из `prompts.ts` и
переиспользуется.

- **Почему включительно через `before`+1день, а не только `since`:** иначе `since` = «начиная
  с» вернёт все письма с этого дня до конца ящика, а не один день. Пользователь ожидает, что
  `дата - 2026-11-03` найдёт письма именно 3 ноября.

### D3: Без явной даты — bounded окно `now − fallbackDays`

Если `дата` не введена, `/find` передаёт `since = now − MAIL_SEARCH_FALLBACK_DAYS` (по умолчанию
180). Это bounded окно: не фетчит весь ящик, но покрывает свежую переписку. Значение
пробрасывается из конфига: `bootstrap` → `BootstrapResult.fallbackDays` → `CliRepl` →
`runFindCommand({ fallbackDays })`.

- **Альтернатива:** `since = 1970-01-01` (весь ящик, как `/find-all` без дат). Отклонена:
  `/find` без даты — типичный поиск свежего письма, фетч всего ящика избыточен и медлен.
  Bounded окно 180 дней покрывает подавляющее большинство случаев; для поиска за пределами
  окна пользователь указывает `дату`. `fallbackDays` настраивается.
- **Дефолт 180** совпадает с `MAIL_SEARCH_FALLBACK_DAYS` (bounded fallback тула) — единое окно.

### D4: Переиспользование `collectAllMessages` без изменений

`collectAllMessages(searchTool, login, args, options?)` уже принимает `FindAllSearchArgs` и
возвращает `{ messages, truncated }`. `/find` вызывает его как есть; `formatMessageList`
выводит `messages`. `truncated` → предупреждение (как в `/find-all`). `maxPages`/`pageSize` —
дефолты `collectAllMessages` (200/50) достаточны.

## Risks / Trade-offs

- **[Риск] Bounded окно 180 дней не найдёт старое письмо при поиске без даты.]** →
  намеренный trade-off (как D3); для заведомо старых писем пользователь указывает `дата`.
  `MAIL_SEARCH_FALLBACK_DAYS` настраивается. Альтернатива (весь ящик) медленна на большом ящике.
- **[Риск] Локальная фильтрация по `from` может вернуть больше/меньше, чем серверный SEARCH.]** →
  локальный фильтр — подстрока (case-insensitive) в адресе или имени; это надёжнее серверного
  SEARCH Яндекса по `FROM` (воспроизведено). Поведение предсказуемо и тестируемо.
- **[Trade-off] Дополнительные Round-Trip'ы пагинации (N страниц вместо 1).]** → принято ради
  надёжности (как в `/find-all`); страницы по 50 конвертов дёшевы по сравнению с фетчем тел.
- **[Риск] Изменение поведения `/find` — теперь всегда пагинирует, даже для 1 письма.]** →
  `collectAllMessages` останавливается на первой пустой странице / `hasMore=false`; для типичного
  случая (1–50 писем в окне) — один запрос. Mitigation: unit-тесты покрывают 1, несколько, пусто.

## Migration Plan

1. Обратно совместимо: мастер `/find` (`promptSearchCriteria`) и формат вывода
   (`formatMessageList`) не меняются — пользовательский интерфейс тот же.
2. Порядок внедрения: (а) экспорт `isoToDate` из `prompts.ts`; (б) переписать `find.ts` на
   `buildSearchArgs` + `collectAllMessages`; (в) `FindCommandDeps.fallbackDays`; (г) проводка
   `fallbackDays` через `bootstrap` → `CliRepl` → `/find`; (д) обновить unit-тесты
   `cli-commands-find.test.ts` под новую семантику.
3. Тесты: unit на `buildSearchArgs` (явная дата → since+before одного дня; без даты → bounded
   since; subject/from не идут на сервер); unit на `/find` (тема+отправитель находятся через
   локальный фильтр; на сервер идут только даты; ничего не найдено; отмена; ошибка тула).
4. `npx tsc --noEmit`, `npm run lint`, `npx vitest run` — все зелёные.
5. Откат: вернуть прямой вызов `searchTool.handler({ login, criteria: {subject, since, from} })`
  без `collectAllMessages`; убрать `fallbackDays` из проводки.

## Open Questions

- Нет: подход переиспользует доказанную машину `/find-all`; bounded окно без даты —
  осознанный trade-off, настраиваемый через `MAIL_SEARCH_FALLBACK_DAYS`.
