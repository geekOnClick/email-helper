# Design

## Context

Тул `mail.search` (спека `mail/search`) уже умеет всё, что нужно новой команде: `subject`, `from`, `since`/`before`,
`limit`/`offset`, возвращает `total`/`hasMore`, и всегда дофильтровывает серверный результат локально по всем
критериям. Проблема `/find` — не в туле, а в его bounded fallback: серверный SEARCH Яндекса по кириллическим
`subject`-литералам ненадёжен (возвращает 0), поэтому `searchAttempt` включает fallback `SINCE now-180д`, после
которого локальная дофильтровка по теме оставляет лишь письма последнего полугодия. Для команды, которая должна найти
**все** письма по теме за весь ящик, этого окна мало.

См. proposal.md — мотивация (одно старое письмо вместо всех).

## Goals / Non-Goals

**Goals:**

- Дать оператору инструмент «найти все письма по теме/отправителю (опц. за диапазон дат) и увидеть объём переписки по
  датам» — без ручного перебора дат в `/find`.
- Обойти 180-дневный баунд fallback, не меняя тул `mail.search` и его спеку.
- Точный полный подсчёт дат (с пагинацией), даже когда писем > лимита страницы.
- Ограничить вывод, чтобы десятки/сотни дат не заливали терминал: максимум 10 строк + «найдено ещё N».

**Non-Goals:**

- Не меняем тул `mail.search` и спеку `mail/search` — команда использует его как есть.
- Не выводим темы/отправителей/UID — только даты и количество (по запросу оператора); детальный просмотр — через
  `/find`/`/analyze` после сужения дат.
- Не вводим сортировку/группировку дат (по месяцам и т.п.) — простой столбец.
- Не меняем `mail.connect`/выбор аккаунта — переиспользуем `ensureMailConnected` + `promptAccount` как `/find`.

## Decisions

### D1: Сервер ищет ТОЛЬКО даты; тема/отправитель — локальный фильтр

Серверный IMAP SEARCH Яндекса по кириллическим `subject`-литералам ненадёжен: возвращает **неполный** результат
(не 0, а подмножество). Тул `mail.search` включает bounded fallback (`SINCE now-180д` + локальная фильтрация), но
только когда серверный поиск вернул **0** — при непустом неполном результате fallback не запускается, и `/find-all`
получает лишь часть писем (баг: «должно быть >20, отдал 3»).

Поэтому `/find-all` **не передаёт `subject`/`from` в серверный поиск вообще** — только диапазон дат (надёжный
IMAP-критерий): `buildSearchArgsFromFindAll` кладёт `since`/`before` в `serverCriteria`, а `subject`/`from`
оставляет для локальной фильтрации. Агрегатор (`collectAllMessages`) получает ВСЕ письма диапазона через
пагинацию и фильтрует по теме/отправителю локально (case-insensitive, нормализация пробелов — см. D3b). Так
находятся все совпадения, независимо от ненадёжности серверного SEARCH по теме.

- **Альтернатива (ранний `since` + subject на сервере)** — не работает: fallback тулa не запускается при непустом
  серверном результате, и неполный поиск по теме «протекает» в выдачу. Отклонено.
- **Альтернатива (менять тул `mail.search`)** — меняет спеку `mail/search` и рискует регрессией `/find` и
  MCP-клиентов. Отклонено: bounded fallback защищает `/find` от фетча всего ящика; ответственность `/find-all` —
  свой собственный подход «даты на сервер, тема локально».
- Если диапазон дат не указан — `since = 1970-01-01` (весь ящик); локальный фильтр по теме/отправителю обязан быть
  задан (иначе это фетч всего ящика). Пустой ввод отменяется (спека «Мастер критериев /find-all», сценарий
  «Пустой ввод без полей — отмена»).

**Риск**: фетч всех писем диапазона (без серверной темы) нагружает сеть на большом ящике. Смягчение: пагинация
(D2) ограничивает память; потолок страниц — предупреждение `truncated`. Это осознанный запрос оператора «найти все».

### D3b: Локальный фильтр темы/отправителя

`matchesLocalFilters`: тема — подстрока `subject` в `m.subject`; отправитель — подстрока `from` в имени или
адресе. Оба — case-insensitive с нормализацией пробелов (`\s+` → один пробел, trim), чтобы «Уроки  истории»
(двойной пробел) и «уроки истории» совпадали. AND по полям.

### D2: Полный подсчёт через пагинацию `mail.search`

`mail.search` возвращает страницу (`messages`, `total`, `hasMore`). Поле `total` — это число UIDs после серверного
поиска *до* локальной дофильтровки, поэтому оно не равно числу писем, реально匹配ших теме. Значит, опираться на
`total` нельзя — нужно агрегировать фактически отфильтрованные `messages` по страницам.

Алгоритм: запрашивать страницы с `limit` (например 50) и увеличивать `offset`, пока `hasMore` не станет `false`;
аккумулировать `messages[].date` из каждой страницы. Защита от зацикливания: остановка при `hasMore === false` либо
при пустой странице, либо по жёсткому上限у итераций (например 200 страниц = 10 000 писем) с сообщением о
достигнутом лимите.

- **Альтернатива**: один вызов с большим `limit` — `total`/`hasMore` всё равно считают UIDs до фильтрации, а фетч
  10 000 конвертов одним вызовом нагружает память и сеть; пагинация стабильнее.
- **Защита**: максимум итераций пагинации (configurable), после которого выводится предупреждение «показаны первые N
  писем, достигнут лимит пагинации».

### D3: Семантика «дата по включительно» — нормализация к `before` на уровне CLI

Тул `mail.search` трактует `since` включительно, `before` исключительно (`msg.date >= before` → отсев в
`matchesCriteria`). Оператор ожидает «дата по 2024-12-31» = включая 31-е. Поэтому команда нормализует `дата по` в
`before` = `<дата> + 1 день` (полночь следующего дня) перед передачей в тул. `дата с` передаётся как `since`
без изменений (полночь указанного дня).

- Нормализация — чистая функция в `prompts.ts`/обработчике, не меняет тул.
- Дата строится как `new Date(year, month-1, day)` (локальная полночь), `before` = `new Date(...); before.setDate(+1)`.

### D4: Размер страницы и потолок пагинации

`limit` страницы = 50 (как дефолт тула). Потолок итераций = 200 (≤10 000 писем). Если достигнут потолок — выводим
найденное + предупреждение, что достигнут лимит и возможны ещё письма.

### D5: Формат вывода — таблица с заголовками (дата, тема, отправитель)

Форматтер `formatFindAllTable(messages)` рисует таблицу с динамической шириной колонок по данным (тема — полностью,
без усечения):
```
Найдено писем: 15
──────────────────────────────────────────────────────────────
Дата письма  | Тема письма          | Отправитель
──────────────────────────────────────────────────────────────
2024-03-01   | Уроки истории        | teacher@school.ru
2024-03-15   | Re: Уроки истории    | ivan@yandex.ru
... (10 строк)
──────────────────────────────────────────────────────────────
найдено ещё 5 писем
```
Заголовки колонок: «Дата письма», «Тема письма», «Отправитель». Отправитель — «Name <email>» при наличии имени,
иначе email; при отсутствии — «неизвестно». Тема нормализуется (переводы строк/табы → пробел). Порядок строк —
как возвращает тул (UID-порядок папки, обычно обратный хронологический); отдельная сортировка не вводится
(Non-Goal). При >10 — первые 10 строк + «найдено ещё N писем». При ≤10 — все строки без «найдено ещё». При 0 —
обработчик выводит «Ничего не найдено.» (форматтер возвращает пустую строку).

## Risks / Trade-offs

- **[Риск] Ранний `since` на огромном ящике без узкого фильтра → большой сетевой фетч.** → Смягчение: команда требует
  хотя бы тему или отправителя (или явный диапазон); пустой ввод отменяется. Осознанный запрос оператора.
- **[Риск] `total` тула не равен числу матчей после локальной фильтрации.** → D2: агрегируем фактически
  отфильтрованные `messages`, не `total`.
- **[Риск] Зацикливание пагинации.** → Жёсткий потолок итераций (200) с предупреждением.
- **[Trade-off] Не показываем темы/UID — оператору нужно сужение дат, чтобы перейти к `/analyze`.** → Принято по
  запросу: цель команды — объём переписки по датам, не детали. Переход к деталям — через `/find` с конкретной датой.
- **[Trade-off] Дополнительный сетевой Round-Trip на пагинацию (N страниц вместо 1).** → Принято ради точного
  подсчёта и стабильности; страницы по 50 конвертов дёшевы по сравнению с фетчем тел.
