# Design: mail-attachment-extension-fix

## Контекст

`mail.downloadAttachments` скачивает вложения через `client.downloadMany(uid, parts, { uid: true })`. Результат — объект `{ [part]: { meta: DownloadMeta, content: Buffer } }`. Код в `downloadAttempt` (`abstract-imap-provider.ts`) формирует имя файла и прогоняет его через `uniqueFilename` → `sanitizeFilename`.

`DownloadMeta` (imapflow) содержит:
- `meta.filename` — имя, декодированное из реального Content-Disposition стрима через `libmime.decodeWords` (надёжнее, чем `bodyStructure`, т.к. проходит через тот же парсер, что и контент);
- `meta.contentType` — MIME-тип стрима (`application/vnd.ms-excel`, `application/pdf` и т.д.);
- `meta.disposition`, `meta.charset`, `meta.encoding` и пр.

### Воспроизведение бага (реальный ящик `kozloww1508@yandex.ru`, письмо «Платежные документы за отопление» от Автозаводской ТЭЦ, UID 35146)

Зондирование реального письма показало:
```
meta.filename    = "Акт-1292-2-30-2608 период-Август 2026 г..xls"   ← ДВЕ точки перед xls (баг отправителя)
meta.contentType = "application/octet-stream"                        ← не application/vnd.ms-excel
att.filename     = то же (bodyStructure совпадает с meta.filename)
```
Отправитель формирует имя с **двойной точкой** перед расширением (`г..xls`). Имя корректно открывается как `.xls`. Но `sanitizeFilename` его калечит:

```js
clean = clean.replace(/\.\./g, '').replace(/[\\/]/g, '');
```

`replace(/\.\./g, '')` вырезает **любые две подряд идущие точки**, а не только path-traversal-сегмент `..`. В имени `...г..xls` подстрока `..` перед `xls` матчится и удаляется → `...гxls`. Обе точки пропадают, расширение теряется, файл сохраняется как `...гxls`.

Подтверждено на диске: `downloadAttachments` записал файл `Акт-1292-2-30-2608 период-Август 2026 гxls` (0 точек перед xls) при входном `...г..xls`. На `pdf` бага не воспроизводится, т.к. pdf-вложения не имеют двойных точек в имени.

### Итог причин

1. **Главная (чинит баг):** `sanitizeFilename` жадно вырезает `..` и калечит легитимные имена с двойными точками.
2. **Вторичная (улучшение):** имя берётся только из `bodyStructure` (`att.filename`), а `meta.filename`/`meta.contentType` игнорируются. Не причина бага, но упускает надёжный источник.
3. **Страховка:** отсутствует восстановление расширения для редкого случая, если отправитель пришлёт именно слипшееся имя (`...гxls` без точки), а не имя с двойной точкой.

## Решение

### D1. Исправление `sanitizeFilename` (главный фикс)

Заменить жадный `replace(/\.\./g, '')` на **path-component-aware** вырезание `..`: вырезать `..` только как path-сегмент (между разделителями `/`/`\`, или в начале/конце имени), а не любые две подряд точки в середине имени.

Реализация (вариант): разбить имя на сегменты по `/` и `\`, отфильтровать сегменты, равные `..` или `.` (path-traversal), и пересобрать через `basename`-эквивалент. Поскольку `basename()` (шаг 1) уже убирает каталоги, шаг вырезания `..` остаётся как защита от обхода `basename` (например, когда basename возвращает `..` или имя состоит только из точек). Конкретно:

```js
// после basename:
// вырезаем path-component '..' — но НЕ любые две точки внутри имени
// имя '..' или '.' или только-точки → дефолт (уже покрыто шагом 3)
// иначе — оставить двойные точки в середине имени как есть
```

Тест-инварианты:
- `Акт-...период-Август 2026 г..xls` → `Акт-...период-Август 2026 г..xls` (двойная точка сохранена) — **главный регресс-тест**;
- `../../etc/passwd` → `passwd` (path-traversal обеззаражен);
- `..\\..\\windows\\system32` → `windowssystem32` (обратные слеши вырезаны);
- `...` → `attachment` (только точки → дефолт, текущее поведение);
- `report.pdf` → `report.pdf` (без изменений).

### D2. Приоритет имени из `meta.filename`

В `downloadAttempt`, при формировании имени для сохранения, использовать приоритет:
```
const rawName = dl.meta?.filename || att.filename;
```
`dl.meta.filename` — декодированное имя из реального потока; если отправитель в Content-Disposition стрима прислал корректное имя (с точкой), оно победит. Если `meta.filename` пуст — fallback на `att.filename` (текущее поведение, обратно совместимо). Поля `meta` типизированы как `Record<string, unknown>` (см. `types.ts` `ImapClient.downloadMany`), поэтому фильтруются через `typeof ... === 'string'`.

### D3. Восстановление расширения (страховка)

Хелпер `ensureExtension(name: string, contentType?: string): string` в `src/tools/mail/filename.ts` (уже реализован в рамках change):

1. **Если имя уже оканчивается на `.ext` (точка + 1–5 букв)** — вернуть как есть. Сохраняет поведение для `report.pdf` и `...г..xls` (оба оканчиваются на `.xls`/`.pdf`).
2. **Иначе — распознать известное расширение в конце имени без точки** (список из `mime-extensions.ts`, отсортированный по убыванию длины, чтобы `xlsx` раньше `xls`). Если имя оканчивается на `xls` без предшествующей точки — вставить точку: `...гxls` → `...г.xls`.
3. **Иначе — если известен `contentType`** — добавить расширение из MIME-карты: `документ` + `application/pdf` → `документ.pdf`.
4. **Иначе — вернуть имя как есть** (не выдумывать расширение; `application/octet-stream` не даёт оснований для расширения).

Карта MIME→расширение в модуле `src/tools/mail/mime-extensions.ts` (`extFromContentType` + `KNOWN_EXTENSIONS`).

### D4. Порядок применения в `downloadAttempt`

```
const rawName = metaFilename || att.filename;
const withExt = ensureExtension(rawName, metaContentType);
const safeName = await uniqueFilename(absDir, withExt);  // внутри вызывает sanitizeFilename
```

`ensureExtension` → `uniqueFilename` → `sanitizeFilename`. С исправленным `sanitizeFilename` (D1) имя `...г..xls` проходит насквозь без потерь точек. Слипшееся имя `...гxls` чинится `ensureExtension` на шаге D3. Суффикс коллизии `-N` добавляется к имени с уже восстановленным расширением.

### D5. Безопасность

Исправление `sanitizeFilename` (D1) не ослабляет path-traversal guard: path-component `..` по-прежнему вырезается; убирается только ложное срабатывание на двойных точках внутри имени. `basename()` на шаге 1 сохранён. Восстановленное расширение (D3) содержит только `[A-Za-z0-9]`. `isInsideDir`-проверка сохраняется.

### D6. Что НЕ делаем

- Не пытаемся «угадать» расширение по магическим байтам контента — выходит за рамки; достаточно имени + content-type.
- Не нормализуем двойные точки в одну (не превращаем `г..xls` в `г.xls`) — имя сохраняется как пришло от отправителя; ОС и Excel корректно открывают `..xls` как `.xls`.
- Не переименовываем уже корректные имена.
- Не меняем `extractAttachments` и метаданные, возвращаемые `mail.fetch` (там расширение не критично — это список, не файл на диске).
- Не добавляем опцию конфигурации — поведение фиксировано и обратно совместимо.

## Альтернативы

- **Только фикс `sanitizeFilename`, без `ensureExtension`/`meta.filename`.** Чинит наблюдаемый баг (`...г..xls`), но не покрывает гипотетический случай слипшегося имени (`...гxls` без точки) и не использует более надёжный `meta.filename`. `ensureExtension` и приоритет `meta.filename` остаются как дешёвая страховка и улучшение, уже реализованные в change.
- **Нормализация двойных точек в одну (`г..xls` → `г.xls`).** Дополнительная сложность и риск сломать легитимные имена с двумя точками (например, `ver.1.2.pdf`). Отклонено — имя сохраняется как есть.

## Риски

- **D1 слишком узкое вырезание `..`** — если реализовать неверно, можно пропустить path-traversal. Покрытие тестами: `../../etc/passwd`, `..\\..\\windows`, имя с легитимной двойной точкой.
- **D3 ложное срабатывание** — имя, случайно оканчивающееся на `xls`/`doc` как часть слова (например `Maxls`). Маловероятно для реальных имён вложений; список ограничен известными офисными расширениями; есть content-type как второй сигнал. Принимаемый риск.
- **`meta.filename` отличается от `att.filename`** — в редких случаях сервер/отправитель формирует их по-разному. Приоритет `meta.filename` даёт более надёжное имя (из реального потока). Если `meta.filename` пуст — fallback на `att.filename`. Обратно совместимо.
