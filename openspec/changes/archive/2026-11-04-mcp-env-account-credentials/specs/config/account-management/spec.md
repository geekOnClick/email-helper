# Spec Delta

## Purpose

Управление списком почтовых аккаунтов, хранящихся в `.env` (`ACCOUNTS`): валидируемое
добавление и обновление записей (`provider`, `login`, `password`, `authStrategy`) с
атомарной персистентностью в файл `.env` (с сохранением прочих переменных и
комментариев), и in-memory реестр аккаунтов как изменяемый источник правды для тулов и
CLI в рамках одного процесса.

## ADDED Requirements

### Requirement: In-memory реестр аккаунтов

Система SHALL предоставлять изменяемый in-memory реестр почтовых аккаунтов, который
инициализируется из `ACCOUNTS` конфигурации `.env` при старте процесса. Реестр SHALL
поддерживать добавление новой записи, обновление существующей записи (по совпадению
`login`), поиск по паре `(provider, login)` и возврат полного списка аккаунтов. Реестр
SHALL быть единственным источником правды об аккаунтах для тулов и CLI в рамках процесса.

#### Scenario: Инициализация из .env при старте

- **WHEN** процесс стартует с валидным `ACCOUNTS` в `.env`
- **THEN** реестр содержит все аккаунты из `ACCOUNTS`, доступные для поиска по `(provider, login)`

#### Scenario: Поиск аккаунта по паре provider+login

- **WHEN** запрашивается аккаунт по валидной паре `(provider, login)`, присутствующей в реестре
- **THEN** система возвращает аккаунт с его `password` и `authStrategy`

#### Scenario: Аккаунт не найден по паре provider+login

- **WHEN** запрашивается аккаунт по паре `(provider, login)`, отсутствующей в реестре
- **THEN** система возвращает отсутствие аккаунта, не раскрывая пароли других аккаунтов

#### Scenario: Добавление нового аккаунта в реестр

- **WHEN** в реестр добавляется новая запись с уникальным `login`
- **THEN** запись становится доступна для поиска по `(provider, login)` немедленно, без перезапуска процесса

#### Scenario: Обновление существующего аккаунта в реестре

- **WHEN** в реестр добавляется запись с `login`, уже присутствующим в реестре (с подтверждением перезаписи)
- **THEN** система заменяет прежнюю запись новой (обновляя `password`, `provider`, `authStrategy`), и прежний пароль более недоступен через реестр

### Requirement: Валидация записи аккаунта

Система SHALL валидировать поля записи аккаунта при добавлении/обновлении: `provider`
SHALL быть `yandex` или `outlook`; `login` SHALL быть непустой строкой; `password` SHALL
быть непустой строкой; `authStrategy` SHALL быть `basic` или `oauth2` (по умолчанию
`basic`). При невалидном поле система SHALL вернуть читаемую ошибку и SHALL NOT
добавлять запись.

#### Scenario: Валидная запись принимается

- **WHEN** добавляется запись с `provider=yandex`, `login=user@yandex.com`, `password=pwd`, `authStrategy=basic`
- **THEN** система принимает запись без ошибок

#### Scenario: Невалидный provider отклоняется

- **WHEN** добавляется запись с `provider=gmail`
- **THEN** система возвращает ошибку о недопустимом `provider` и не добавляет запись

#### Scenario: Пустой пароль отклоняется

- **WHEN** добавляется запись с пустым `password`
- **THEN** система возвращает ошибку об обязательности пароля и не добавляет запись

#### Scenario: Невалидный authStrategy отклоняется

- **WHEN** добавляется запись с `authStrategy=magic`
- **THEN** система возвращает ошибку о недопустимой стратегии и не добавляет запись

### Requirement: Персистентность аккаунтов в .env

Система SHALL при добавлении/обновлении аккаунта сохранять обновлённый массив
`ACCOUNTS` в файл `.env` как JSON-строку, сохраняя при этом все прочие переменные и
комментарии файла `.env` без изменений. Запись SHALL быть атомарной (временный файл +
переименование), чтобы избежать частично записанного файла при сбое. Файл `.env` SHALL
оставаться вне git.

#### Scenario: Новый аккаунт дописывается в ACCOUNTS

- **WHEN** добавляется новый аккаунт, а в `.env` `ACCOUNTS` уже содержит одну запись
- **THEN** в `.env` `ACCOUNTS` становится JSON-массивом из двух записей, прочие переменные файла сохранены

#### Scenario: Существующий аккаунт обновляется в ACCOUNTS

- **WHEN** обновляется аккаунт с уже присутствующим в `ACCOUNTS` `login`
- **THEN** в `.env` `ACCOUNTS` сохраняется массив с обновлённой записью (новый пароль), остальные записи не меняются

#### Scenario: Прочие переменные и комментарии .env сохраняются

- **WHEN** система записывает обновлённый `ACCOUNTS` в `.env`
- **THEN** все прочие переменные окружения и комментарии файла `.env` остаются без изменений

#### Scenario: Атомарная запись при сбое

- **WHEN** запись `.env` прерывается (сбой диска)
- **THEN** исходный файл `.env` не повреждается частичной записью благодаря временному файлу и переименованию

#### Scenario: .env остаётся вне git

- **WHEN** система записывает обновлённый `ACCOUNTS` в `.env`
- **THEN** файл `.env` не начинает отслеживаться git (остаётся в `.gitignore`)

### Requirement: Обработка дубликата login при добавлении

При добавлении записи с `login`, уже присутствующим в реестре, система SHALL запросить
явное подтверждение перезаписи (да/нет) до изменения данных. Без подтверждения система
SHALL NOT изменять ни реестр, ни `.env`. Если подтверждено — система обновляет запись
(включая `password`, `provider`, `authStrategy`).

#### Scenario: Дубликат login без подтверждения — отмена

- **WHEN** добавляется запись с уже существующим `login` и оператор отказывается от перезаписи
- **THEN** система не изменяет реестр и `.env`, прежняя запись сохраняется

#### Scenario: Дубликат login с подтверждением — обновление

- **WHEN** добавляется запись с уже существующим `login` и оператор подтверждает перезапись
- **THEN** система обновляет запись в реестре и в `.env`, прежний пароль заменяется новым
