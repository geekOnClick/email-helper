# Design

## Context

Текущий CLI-транспорт (`src/transport/cli/`) после change `cli-smart-commands` имеет guided-команды `/analyze`, `/analyze-many`, `/analyze-attachments`, `/smart-send`, `/add-account`, построенные поверх тулов реестра `mail.*`. Команды поиска требуют ручного ввода структурированных критериев построчным мастером (`promptSearchCriteria` для `/analyze`, `promptFindAllCriteria` для `/analyze-many`). Машина пакетного поиска `collectAllMessages` (`commands/search-aggregator.ts`) реализует локальную фильтрацию темы/отправителя + пагинацию: серверу передаётся только диапазон дат, тема/отправитель фильтруются локально (серверный IMAP SEARCH Яндекса по ним ненадёжен).

One-shot паттерн LLM-вызова уже применён в `/smart-send` (`commands/smart-send.ts`): `RouterAiClient.chat({ messages, role: 'helper' })` без тулов и без субагент-цикла. `BootstrapResult` уже отдаёт `llmClient: RouterAiClient` наружу, а `CliRepl` (`GuidedCommandDeps`) уже имеет `llmClient`, `analyzeManyMaxEmails`, `fallbackDays`.

Конфигурация: `ANALYZE_MANY_MAX_EMAILS` (дефолт 10) — потолок числа писем; `MAIL_SEARCH_FALLBACK_DAYS` (дефолт 180) — bounded-окно. Оба в `src/config/schema.ts` и `BootstrapResult`.

MCP-путь (оркестратор + helper + тулы `mail.*`) не меняется. Изменения только в CLI-слое.

## Goals / Non-Goals

**Goals:**
- Добавить команду `/smart-search`, где пользователь вводит только промпт естественным языком, а LLM разбирает его в критерии поиска.
- Переиспользовать проверенную машину пакетного поиска `collectAllMessages` без изменения её логики.
- Переиспользовать one-shot паттерн `RouterAiClient` (роль `helper`), уже применённый в `/smart-send`.
- Переиспользовать существующий UX выбора аккаунта (`promptAccount`), вывода таблицы писем (`formatMessageList`) и выбора UID (`promptUid`).
- Сохранить MCP-путь и тулы `mail.*` без изменений.

**Non-Goals:**
- Не меняем тулы `mail.*` (`mail.search`, `mail.fetch` и др.) и их спеки.
- Не вводим субагента для поиска (one-shot парсинг промпта достаточен; без tool-loop).
- Не делаем LLM-анализ найденного письма (это `/analyze`; `/smart-search` — чистый поиск/просмотр с телом письма).
- Не меняем мастер `promptFindAllCriteria`/`promptSearchCriteria` и остальные команды.
- Не вводим новые env-значения (переиспользуем `ANALYZE_MANY_MAX_EMAILS` и `MAIL_SEARCH_FALLBACK_DAYS`).

## Decisions

### D1: One-shot LLM-парсинг промпта в структурированные критерии

Команда `/smart-search` после получения промпта делает один прямой вызов `RouterAiClient.chat({ messages, role: 'helper' })` (без тулов, без субагент-цикла), который возвращает структурированные критерии: `{ тема?: string, отправитель?: string, дата с?: ISO, дата по?: ISO, количество?: number }`. Системный промпт задаёт формат ответа (JSON), модель только разбирает естественный язык в поля — не выполняет поиск. Команда разбирает ответ и формирует `FindAllSearchArgs` + `количество`.

Это повторяет паттерн `/smart-send` (D4 из `cli-smart-commands`): один LLM-вызов для преобразования «промпт → структурированный домен», без регистрации нового субагента и без tool-loop. Bootstrap уже отдаёт `llmClient`.

**Альтернатива (а):** субагент с доступом к тулам `mail.search` — отказались (дороже по токенам/латентности, ломает установленный one-shot паттерн, усложняет контроль потолка писем).
**Альтернатива (b):** ручной мастер критериев — отказались (это и есть существующие `/analyze`/`/analyze-many`; цель команды — промпт одной строкой).

### D2: Переиспользование `collectAllMessages` + bounded-окно `fallbackDays`

Парсинг промпта даёт `subject`/`from`/`дата с`/`дата по` → формируем `FindAllSearchArgs` (`serverCriteria` = только даты, `subject`/`from` для локальной фильтрации) и вызываем существующий `collectAllMessages(searchTool, login, args)`. Логика агрегатора (пагинация + локальная фильтрация) не меняется.

Bounded-окно: если промпт не указывает дату, `serverCriteria.since` = `now − MAIL_SEARCH_FALLBACK_DAYS` (дефолт 180), `before` не задаётся. Это отличается от `buildSearchArgsFromFindAll` (которая при отсутствии дат использует `EARLIEST_SINCE` = 1970 = весь ящик) — `/smart-search` собирает `serverCriteria` отдельно, не через `buildSearchArgsFromFindAll`, чтобы получить bounded-окно (быстро, достаточно для типичных «последних» писем). При наличии явных дат в промпте — `since`/`before` из них (дата включительно → `before` = полночь следующего дня, как `isoToDate`).

`fallbackDays` уже есть в `BootstrapResult` и `GuidedCommandDeps` (прокинуто для `/analyze-many`), переиспользуем без новых полей.

**Альтернатива:** весь ящик (1970) — отказались (медленно для крупных ящиков; «последнее письмо» почти всегда в пределах 180 дней; пользователь может указать дату явно).

### D3: Сортировка по дате убыванием + top-N

`collectAllMessages` возвращает письма в порядке серверной выдачи (не гарантирован). Команда сортирует найденные по `email.date` убыванием (новые сверху) и берёт top-N, где N = `min(количество из промпта, ANALYZE_MANY_MAX_EMAILS)` (дефолт N=1, если промпт не называет число). Сортировка локальная, после агрегатора, до вывода/выбора UID.

Потолок `ANALYZE_MANY_MAX_EMAILS` (дефолт 10) переиспользуется как хард-кап N (нельзя запросить больше) — это ограничивает и число фетчей тел, и размер вывода. При превышении — тихое ограничение до потолка (без предупреждения, т.к. пользователь просил больше, чем система гарантирует; N ограничен потолком).

**Альтернатива:** без потолка — отказались (риск фетча сотен тел и переполнения контекста; противоречит сложившемуся паттерну `ANALYZE_MANY_MAX_EMAILS`).

### D4: N=1 — показать письмо целиком; N>1 — таблица + выбор UID

- N=1 (или дефолт): после top-1 команда фетчит тело через `mail.fetch` и выводит письмо целиком (отправитель, тема, дата, UID, тело) — БЕЗ LLM-анализа. Переиспользуем `formatDraft`-подобный вывод (или новую `formatEmailFull`), без вызова `analyzer`.
- N>1: команда выводит таблицу найденных top-N через `formatMessageList` (тема, отправитель, дата, UID), затем `promptUid` запрашивает выбор; после выбора — `mail.fetch` + вывод письма целиком (с телом) БЕЗ анализа.

Открытое письмо показывается как «просмотр», не «анализ» — это явное отличие от `/analyze` (который после открытия запускает `analyzer.run`). `/smart-search` не зависит от субагента-анализатора (в `SmartSearchCommandDeps` нет `analyzer`).

**Альтернатива:** всегда таблица даже для N=1 — отказались (пользователь просил «одно письмо» — показать сразу его, без лишнего шага выбора).

## Risks / Trade-offs

- **Качество LLM-парсинга промпта.** One-shot модель (роль `helper`, дешёвая) может неточно разобрать редкие формулировки (например, относительные даты «на прошлой неделе»). Системный промпт SHALL требовать JSON-ответ и валидировать поля (даты ISO, email); при невалидном ответе — сообщение об ошибке парсинга + отмена (без молчаливой отправки некорректных критериев на сервер). Тестируем на типовых промптах («последнее письмо от X», «10 писем по теме Y», «письма за август от Z»).
- **Bounded-окно vs весь ящик.** 180 дней может не найти «последнее письмо», если оно старше. Компромисс: скорость против полноты. Пользователь может явно указать дату в промпте. Документируем в справке команды.
- **Сортировка по дате.** `collectAllMessages` отдаёт `EmailMessage` с полем `date` (Date); сортировка локальная над всеми найденными письмами в окне. При достижении потолка пагинации (`truncated: true`) «top-N» может быть не точным (не все письма собраны) — выводим предупреждение о пагинации (как `/analyze-many`).
- **Потолок как дефолт N.** Если промпт не называет число, дефолт N=1 (одно письмо), а не весь потолок — это быстрее и соответствует типичному «найди последнее письмо». Потолок `ANALYZE_MANY_MAX_EMAILS` ограничивает N сверху, когда пользователь просит больше.
