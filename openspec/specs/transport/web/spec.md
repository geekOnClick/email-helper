# transport/web Specification

## Purpose

Веб-транспорт email-helper: React + Vite SPA с Material-UI поверх встроенного
Node HTTP REST API. Даёт читаемый макет почтового клиента (список писем слева,
тело/анализ справа) и формы для операций, альтернативу CLI REPL поверх того же
ядра (тулы, агенты, LLM-клиенты).

## Requirements

### Requirement: Встроенный HTTP-сервер

Система SHALL поднимать Node HTTP-сервер (встроенный `node:http`, без
Express/Fastify) в том же процессе, что и CLI, переиспользуя bootstrap-сборку
агентов/тулов (`bootstrap()`). Сервер SHALL слушать `WEB_HOST:WEB_PORT` (по
умолчанию `127.0.0.1:3000`, localhost-only).

#### Scenario: Запуск веб-сервера

- **WHEN** процесс запускается с режимом web (`npm run web` или `--web`)
- **THEN** система поднимает HTTP-сервер на `WEB_HOST:WEB_PORT`, логирует URL и
  остаётся активным (не завершается, как REPL после quit)

#### Scenario: localhost-only по умолчанию

- **WHEN** `WEB_HOST` не задан в `.env`
- **THEN** сервер слушает `127.0.0.1` и SHALL NOT принимать внешние соединения
  (как MCP HTTP-транспорт)

### Requirement: Обслуживание статики SPA

Сервер SHALL обслуживать собранное SPA из `dist/client/` на корневом маршруте
(`/`) и статику — на `/assets`. При отсутствии собранной сборки SHALL отвечать
`503` с подсказкой пересобрать фронтенд.

#### Scenario: SPA обслуживается на корневом маршруте

- **WHEN** браузер запрашивает `GET /`
- **THEN** сервер отдаёт `dist/client/index.html`

#### Scenario: Отсутствие сборки — подсказка

- **WHEN** `dist/client/` не существует и браузер запрашивает `GET /`
- **THEN** сервер отвечает `503` с JSON-сообщением «соберите фронтенд: npm run web:build»

#### Scenario: CORS для dev-сервера Vite

- **WHEN** в dev-режиме (`web:dev`) фронтенд запущен на порту Vite, а API — на
  `WEB_PORT`
- **THEN** API-сервер SHALL отправлять `Access-Control-Allow-Origin` для
  запросов с dev-origin Vite, чтобы SPA мог обращаться к API в разработке

### Requirement: Маршрутизация REST API

Все REST-эндпоинты SHALL находиться под префиксом `/api`. Неизвестные `/api/*`
маршруты SHALL возвращать `404` JSON-ошибкой; недопустимые методы — `405`.
Ответы SHALL быть JSON; ошибки SHALL иметь форму `{ error, code? }`.

#### Scenario: REST-эндпоинты доступны под /api

- **WHEN** клиент запрашивает `GET /api/accounts`
- **THEN** сервер возвращает `200` с JSON-списком аккаунтов (login + provider,
  без паролей) из реестра bootstrap'а

#### Scenario: Неизвестный маршрут — 404

- **WHEN** клиент запрашивает `/api/unknown`
- **THEN** сервер отвечает `404` с `{ error: "not found" }`

#### Scenario: Пароли не передаются в API

- **WHEN** любой эндпоинт принимает или возвращает данные аккаунта
- **THEN** поле `password` SHALL быть исключено из DTO; пароль извлекается
  бэкендом из `.env` по `login`+`provider`, как в `mail.connect`

### Requirement: Эндпоинты поиска и чтения

Система SHALL предоставить `POST /api/smart-search` (поиск по промпту) и
`GET /api/emails/:accountLogin/:uid` (чтение тела письма). `smart-search`
принимает `{ accountLogin, prompt }` и возвращает `{ messages, total, hasMore }`.
Чтение принимает query `folder` и возвращает полное письмо (`EmailFull`).

#### Scenario: smart-search по промпту

- **WHEN** клиент отправляет `POST /api/smart-search` с `{ accountLogin, prompt }`
- **THEN** сервер парсит промпт LLM в критерии, выполняет `mail.search`, возвращает
  `{ messages: EmailMessage[], total, hasMore }`

#### Scenario: Чтение тела письма

- **WHEN** клиент запрашивает `GET /api/emails/:accountLogin/:uid?folder=`
- **THEN** сервер вызывает `mail.fetch` и возвращает полное письмо (`EmailFull`:
  метаданные + тело + вложения)

#### Scenario: Аккаунт не найден

- **WHEN** эндпоинт получает `accountLogin`, отсутствующий в реестре
- **THEN** сервер отвечает `404` с `{ error: "account_not_found", code }`

### Requirement: Эндпоинты анализа

Система SHALL предоставить `POST /api/analyze`, `POST /api/analyze-many`,
`POST /api/analyze-attachments`, каждый принимающий DTO (`accountLogin` + входные
данные) и возвращающий JSON-отчёт анализа.

#### Scenario: Анализ одного письма

- **WHEN** клиент отправляет `POST /api/analyze` с `{ accountLogin, uid, folder? }`
- **THEN** сервер фетчит письмо, передаёт анализатору (LLM) и возвращает
  `{ analysis }` (отчёт)

#### Scenario: Анализ нескольких писем

- **WHEN** клиент отправляет `POST /api/analyze-many` с критериями поиска
- **THEN** сервер выполняет пакетный анализ и возвращает сводный отчёт

### Requirement: Эндпоинт отправки

Система SHALL предоставить `POST /api/smart-send/generate` (генерация тела) и
`POST /api/smart-send/send` (отправка подтверждённого тела), разделённые для
подтверждения перед отправкой, как в CLI.

#### Scenario: Генерация тела

- **WHEN** клиент отправляет `POST /api/smart-send/generate` с `{ accountLogin, to, subject, prompt }`
- **THEN** сервер возвращает `{ body }` (сгенерированный черновик) без отправки

#### Scenario: Отправка подтверждённого тела

- **WHEN** клиент отправляет `POST /api/smart-send/send` с подтверждённым `{ accountLogin, to, subject, body }`
- **THEN** сервер вызывает `mail.send` и возвращает результат отправки

### Requirement: Эндпоинты аккаунтов и папок

Система SHALL предоставить `GET /api/accounts` (список без паролей),
`POST /api/accounts` (добавление), `GET /api/folders/:accountLogin` (список
папок ящика).

#### Scenario: Список аккаунтов

- **WHEN** клиент запрашивает `GET /api/accounts`
- **THEN** сервер возвращает массив `{ login, provider, authStrategy }` без паролей

#### Scenario: Добавление аккаунта

- **WHEN** клиент отправляет `POST /api/accounts` с полями аккаунта
- **THEN** сервер вызывает чистую функцию сохранения и возвращает `201` с `{ login, provider }` без пароля

### Requirement: Макет почтового клиента

SPA SHALL использовать макет почтового клиента: тулбар команд сверху, список
писем слева, чтение тела письма и анализа справа. Правая панель SHALL быть
основной зоной чтения и SHALL занимать большую часть ширины экрана.

#### Scenario: Двухпанельный макет при выборе письма

- **WHEN** пользователь выбирает письмо в левом списке
- **THEN** правая панель отображает тело выбранного письма; список остаётся
  видимым слева

#### Scenario: Тулбар команд

- **WHEN** отображается главное окно
- **THEN** вверху видны кнопки/меню команд: Smart Search, Analyze, Analyze Many,
  Analyze Attachments, Smart Send, Add Account

#### Scenario: Анализ в правой панели

- **WHEN** запускается анализ (письма/вложений)
- **THEN** результат LLM-анализа SHALL отображаться в правой панели в
  читаемом структурированном виде (заголовки, абзацы, списки), а не сырым текстом

### Requirement: Выбор аккаунта через дропдаун

Для любой операции, требующей аккаунт, SPA SHALL предоставить дропдаун выбора
аккаунта, заполненный из `GET /api/accounts`. При отсутствии аккаунтов SHALL
отображаться подсказка «добавьте аккаунт через Add Account».

#### Scenario: Дропдаун заполнен аккаунтами

- **WHEN** SPA загружается
- **THEN** дропдаун содержит все аккаунты из `GET /api/accounts` (login +
  provider), без паролей

#### Scenario: Нет аккаунтов — подсказка

- **WHEN** `GET /api/accounts` возвращает пустой список
- **THEN** дропдаун пуст и отображается подсказка добавить аккаунт

### Requirement: Формы операций (гибрид UX)

Для операций без пошагового LLM-диалога (поиск, отправка) SPA SHALL
использовать единые формы с полями вместо пошагового wizard. Для операций с
LLM-анализом SHALL сохраняться поток: пользователь выбирает входные данные →
запускает анализ → видит отчёт в правой панели. Форма `smart-send` SHOULD
предлагать подтверждение перед отправкой.

#### Scenario: Форма smart-send с подтверждением

- **WHEN** пользователь заполняет форму smart-send и нажимает «Сгенерировать»
- **THEN** SPA отображает сгенерированное тело для редактирования; кнопка
  «Отправить» подтверждает отправку, «Отмена» — отменяет без отправки

#### Scenario: Анализ — запуск и отчёт

- **WHEN** пользователь выбирает письмо и нажимает «Analyze»
- **THEN** SPA показывает индикатор прогресса, затем отчёт анализатора в правой
  панели

### Requirement: Читаемый рендер письма и вложений

SPA SHALL рендерить тело письма читаемо: HTML-письмо — в безопасном
санитизированном виде, plain-text — с сохранением переносов. Список вложений
SHALL отображаться с именем, размером и кнопкой скачивания.

#### Scenario: HTML-письмо санитизировано

- **WHEN** тело письма содержит HTML
- **THEN** SPA рендерит его после санитизации (удалены скрипты, внешние ресурсы)
  в ограниченной области прокрутки

#### Scenario: Скачивание вложения

- **WHEN** пользователь нажимает «Скачать» на вложении
- **THEN** SPA запрашивает `mail.downloadAttachments` через API и инициирует
  скачивание файла в браузере

### Requirement: Конфигурация веб-сервера

Система SHALL читать конфигурацию веб-сервера из `.env`: `WEB_PORT` (по
умолчанию `3000`), `WEB_HOST` (по умолчанию `127.0.0.1`). `package.json`
SHALL содержать скрипты `web`, `web:dev`, `web:build`.

#### Scenario: Порт из .env

- **WHEN** `.env` содержит `WEB_PORT=8080`
- **THEN** веб-сервер слушает порт `8080`

#### Scenario: Скрипт web поднимает сервер

- **WHEN** выполняется `npm run web`
- **THEN** процесс запускается в режиме web (без REPL), поднимает HTTP-сервер и
  логирует URL
