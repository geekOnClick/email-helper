# mail/search Specification

## Purpose

Поиск писем в почтовом ящике по критериям (тема, отправитель, получатель, дата, флаги) с указанием папки и направления (входящие/исходящие), возврат метаданных без тел.

## Requirements

### Requirement: Поиск по теме

Система SHALL искать письма, тема которых содержит заданную подстроку (без учёта регистра), в указанной папке. Результат SHALL содержать UID, тему, отправителя, дату, флаги.

#### Scenario: Найдены письма по теме

- **WHEN** ищем письма с темой «отчёт» в папке «Входящие»
- **THEN** система возвращает список метаданных писем, в темах которых есть «отчёт»

#### Scenario: Ничего не найдено

- **WHEN** ищем письма с темой, которой нет, в папке
- **THEN** система возвращает пустой список

### Requirement: Поиск по отправителю

Система SHALL искать письма, чей отправитель (From) содержит заданную подстроку.

#### Scenario: Найдены письма от отправителя

- **WHEN** ищем письма от отправителя «ivanov@example.com»
- **THEN** система возвращает метаданные писем, у которых From содержит «ivanov@example.com»

### Requirement: Поиск по дате

Система SHALL искать письма, полученные после (`since`) и/или до (`before`) указанной даты.

#### Scenario: Письма за период

- **WHEN** ищем письма с `since` = 2026-10-01 и `before` = 2026-10-31
- **THEN** система возвращает метаданные писем, полученных в этом периоде

### Requirement: Поиск по папке и направлению

Система SHALL искать в указанной папке. Если задано направление `incoming` — система SHALL искать в папке `\Inbox`; `outgoing` — в `\Sent`. Явно заданная папка имеет приоритет над направлением.

#### Scenario: Поиск во входящих через направление

- **WHEN** ищем письма с направлением `incoming` и без явной папки
- **THEN** система открывает папку «Входящие» (`\Inbox`) и ищет в ней

#### Scenario: Явная папка приоритетнее направления

- **WHEN** ищем с направлением `incoming` и папкой «Archive»
- **THEN** система ищет в «Archive»

### Requirement: Поиск по флагам

Система SHALL поддерживать фильтр по флагам: непрочитанные (`unseen`), помеченные (`flagged`), отвеченные (`answered`).

#### Scenario: Только непрочитанные

- **WHEN** ищем с флагом `unseen=true`
- **THEN** система возвращает только непрочитанные письма

### Requirement: Ограничение и постраничность

Система SHALL поддерживать ограничение количества результатов (`limit`, по умолчанию 50). Результат SHALL содержать общее число найденных и флаг `hasMore`.

#### Scenario: Ограничение результатов

- **WHEN** найдено 100 писем, `limit` = 50
- **THEN** система возвращает 50 элементов, `hasMore` = true

#### Scenario: По умолчанию 50

- **WHEN** критерии без limit
- **THEN** система применяет limit = 50

### Requirement: Требуется активная сессия

Система SHALL отклонять поиск, если для данного логина нет активной IMAP-сессии (созданной тулом `mail.connect`).

#### Scenario: Поиск без подключения

- **WHEN** ищем письма, но сессия для логина не установлена
- **THEN** система возвращает ошибку «подключение не установлено»

### Requirement: Метаданные без тел

Система SHALL возвращать только метаданные писем (UID, тема, отправитель, получатель, дата, флаги, размер), без тел писем. Тело — отдельный тул `mail.fetch`.

#### Scenario: Результат содержит метаданные

- **WHEN** поиск вернул письма
- **THEN** каждое содержит UID, тему, отправителя, дату, флаги и не содержит body

### Requirement: Секреты в ошибках

Система SHALL NOT включать учётные данные или токены в сообщения об ошибках поиска.

#### Scenario: Ошибка поиска без раскрытия секрета

- **WHEN** поиск завершается ошибкой
- **THEN** сообщение об ошибке не содержит пароля и access token

### Requirement: Ограничение client-side фолбэкка

Когда серверный IMAP SEARCH по текстовому критерию (`subject`, `from`, `to`) возвращает пустой результат, система MAY выполнить client-side фолбэкк (fetch метаданных и локальную фильтрацию), но SHALL NOT fetch'ить всю папку (`1:*`). Фолбэкк SHALL сужать диапазон fetch'а надёжными серверными критериями из запроса, а при их отсутствии — `SINCE` по умолчанию.

#### Scenario: Фолбэкк сужается имеющимся критерием since

- **WHEN** серверный поиск по `subject` вернул `0`, а в запросе задан `since`
- **THEN** client-side фолбэкк fetch'ит метаданные только писем с `internalDate >= since` (серверный `SINCE`), а не всей папки, и фильтрует их локально по `subject`

#### Scenario: Фолбэкк сужается имеющимся критерием from

- **WHEN** серверный поиск по `subject` вернул `0`, а в запросе задан `from`
- **THEN** client-side фолбэкк выполняет серверный поиск по `from`, fetch'ит метаданные только по найденным UID'ам и фильтрует их локально по `subject`, не обращаясь к `1:*`

#### Scenario: Фолбэкк при запросе только subject — SINCE по умолчанию

- **WHEN** серверный поиск по `subject` вернул `0`, и в запросе нет `since`/`before`/`from`/`to`/флагов
- **THEN** client-side фолбэкк применяет серверный `SINCE` = последние `MAIL_SEARCH_FALLBACK_DAYS` дней (по умолчанию 180) и fetch'ит метаданные только в этом диапазоне, не по всей папке

#### Scenario: Фолбэкк не обращается ко всей папке

- **WHEN** срабатывает client-side фолбэкк при любом сочетании критериев
- **THEN** система не выполняет `fetchAll('1:*')` по всей папке; диапазон fetch'а всегда сужен надёжными критериями или `SINCE` по умолчанию

### Requirement: Дофильтровка серверного результата

Система SHALL ALWAYS применять локальную фильтрацию по всем текстовым критериям (`subject`, `from`, `to`) и критериям даты (`since`, `before`) к метаданным, полученным серверным поиском, — не только при пустом серверном ответе. Это гарантирует, что ненадёжный серверный поиск (когда IMAP-сервер применяет только часть текстовых критериев, например только `SINCE`, а кириллический `SUBJECT`-литерал игнорирует) не вернёт ложный непустой набор, не соответствующий теме.

#### Scenario: Ложные совпадения сервера отсекаются локально

- **WHEN** серверный поиск по `subject` + `since` вернул письма, тема которых не содержит заданную подстроку (сервер применил только `SINCE`)
- **THEN** система дофильтровывает результат локально и не возвращает письма, не соответствующие `subject`

#### Scenario: Точные совпадения сохраняются

- **WHEN** серверный поиск по `subject` вернул письма, действительно содержащие подстроку в теме
- **THEN** система возвращает их после локальной дофильтровки (поведение поиска по теме не ухудшается)

### Requirement: Таймаут операции поиска

Система SHALL ограничивать длительность одного вызова `mail.search` таймаутом `MAIL_OP_TIMEOUT_MS` (по умолчанию 30000 мс). При превышении система SHALL прервать операцию и вернуть ошибку с понятным сообщением, не оставляя висящий вызов. Таймаут применяется к совокупности серверного поиска, фолбэкка и fetch'а метаданных в рамках одной попытки (до учёта повторов).

#### Scenario: Поиск прерывается по таймауту

- **WHEN** операция поиска не укладывается в `MAIL_OP_TIMEOUT_MS` (например, серверный поиск или фолбэкк затягиваются)
- **THEN** система прерывает операцию и возвращает ошибку, сообщающую о превышении таймаута, без зависания вызова

#### Scenario: Быстрый поиск не обрывается

- **WHEN** операция поиска укладывается в `MAIL_OP_TIMEOUT_MS`
- **THEN** система возвращает нормальный результат, таймаут не срабатывает

### Requirement: Повтор операции поиска при обрыве соединения

При обрыве IMAP-соединения во время поиска (ошибки вида `Connection not available` и иные сетевые сбои, включая `подключение не установлено` при `client === null` после неудачного/невыполненного переподключения) система SHALL переподключить IMAP-сессию и повторить поиск, до `MAIL_OP_MAX_RETRIES` повторов (по умолчанию 2). Переподключение SHALL использовать существующий lifecycle провайдера (закрытие старой сессии и новое подключение) без изменения учётных данных аккаунта. Если все повторные попытки исчерпаны и соединение не восстановлено — система SHALL вернуть ошибку, маскирующую секреты.

#### Scenario: Обрыв соединения — повтор с переподключением

- **WHEN** во время поиска IMAP-соединение обрывается (`Connection not available`)
- **THEN** система переподключает сессию и повторяет поиск; при успехе на повторе возвращает нормальный результат

#### Scenario: Успех на первой попытке — без повторов

- **WHEN** поиск завершается успешно без обрыва соединения
- **THEN** система не выполняет переподключение и лишние повторы, возвращает результат сразу

#### Scenario: Исчерпание повторов — ошибка

- **WHEN** обрыв соединения повторяется чаще `MAIL_OP_MAX_RETRIES`
- **THEN** система возвращает ошибку, сообщающую о недоступности соединения, с замаскированными секретами

#### Scenario: Секреты маскируются в ошибке повтора

- **WHEN** повтор с переподключением завершается ошибкой аутентификации или соединения
- **THEN** сообщение об ошибке не содержит пароля приложения, логина в открытом виде или access token

#### Scenario: «Подключение не установлено» — повтор с переподключением

- **WHEN** операция поиска падает с ошибкой `подключение не установлено` (client обнулён после неудачного/невыполненного переподключения), а попытки ещё остались
- **THEN** система тратит попытку на переподключение и повторяет поиск; при успехе возвращает нормальный результат

#### Scenario: Дефолт потолка повторов — 2

- **WHEN** конфигурация не задаёт `MAIL_OP_MAX_RETRIES`
- **THEN** система использует значение по умолчанию 2 (итого до 3 попыток на операцию: первичная + 2 повтора)
