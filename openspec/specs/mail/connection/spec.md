# mail/connection Specification

## Purpose

Подключение к почтовному ящику по IMAP (Яндекс, Outlook) и получение списка папок, с плавающей стратегией аутентификации `basic` | `oauth2` (Microsoft device code flow для Outlook при отказе basic-auth).

## Requirements

### Requirement: Подключение к ящику по IMAP

Система SHALL устанавливать защищённое IMAP-соединение с сервером провайдера по учётным данным аккаунта и возвращать результат подключения (Яндекс — `imap.yandex.ru:993`, Outlook — `outlook.office365.com:993`, Mail.ru Group — `imap.mail.ru:993`). Вызов тулa `mail.connect` SHALL принимать только `login` и `provider`; пароль SHALL извлекаться сервером из реестра аккаунтов (инициализированного из `ACCOUNTS` в `.env`) по паре `(provider, login)`. Система SHALL NOT принимать пароль или иные учётные данные в аргументах вызова тулa.

#### Scenario: Успешное подключение к Яндекс с паролем приложения

- **WHEN** запрашивается подключение к Яндекс-аккаунту с корректным логином и паролем приложения
- **THEN** система устанавливает IMAP-соединение с `imap.yandex.ru:993` (TLS) и возвращает успешный результат

#### Scenario: Успешное подключение к Outlook с выбранной стратегией

- **WHEN** запрашивается подключение к Outlook-аккаунту с корректными учётными данными и работающей стратегией аутентификации
- **THEN** система устанавливает IMAP-соединение с `outlook.office365.com:993` (TLS) и возвращает успешный результат

#### Scenario: Успешное подключение к Mail.ru с паролем приложения

- **WHEN** запрашивается подключение к аккаунту Mail.ru Group (`@mail.ru`/`@inbox.ru`/`@list.ru`/`@bk.ru`) с корректным логином и паролем приложения, стратегией `basic`
- **THEN** система устанавливает IMAP-соединение с `imap.mail.ru:993` (TLS) и возвращает успешный результат

- **WHEN** запрашивается подключение к Outlook-аккаунту с корректными учётными данными и работающей стратегией аутентификации
- **THEN** система устанавливает IMAP-соединение с `outlook.office365.com:993` (TLS) и возвращает успешный результат

#### Scenario: Подключение с динамическими кредами, переданными вызывающим агентом

- **WHEN** вызов тулa `mail.connect` содержит блок `credentials` с паролем (динамические креды)
- **THEN** система не принимает пароль по MCP и требует только `provider` + `login`; пароль для авторизации извлекается сервером из `ACCOUNTS` (`.env`), динамическая передача кред исключена

#### Scenario: Динамические креды опущены — fallback на конфигурацию .env

- **WHEN** вызов тулa `mail.connect` содержит `provider` и `login` без блока `credentials`
- **THEN** система ищет аккаунт по паре `(provider, login)` в `ACCOUNTS` (`.env`), извлекает пароль и подключается с ним

#### Scenario: Динамические креды опущены и аккаунт не найден в .env

- **WHEN** вызов тулa `mail.connect` содержит `provider` и `login`, и аккаунт с этой парой отсутствует в `ACCOUNTS`
- **THEN** система возвращает структурированную ошибку `account_not_found` и не пытается подключиться

#### Scenario: Provider не соответствует заведённому аккаунту

- **WHEN** вызов тулa `mail.connect` содержит `login`, для которого в `ACCOUNTS` заведён аккаунт, и `provider`, не совпадающий с заведённым
- **THEN** система возвращает структурированную ошибку `provider_mismatch` и не подключается

#### Scenario: Неверные учётные данные

- **WHEN** учётные данные аккаунта отклонены сервером
- **THEN** система возвращает ошибку аутентификации с понятным сообщением, не раскрывая секрет

#### Scenario: Сервер недоступен

- **WHEN** IMAP-сервер недоступен по сети или превышен таймаут подключения
- **THEN** система возвращает ошибку подключения с указанием провайдера и причины

### Requirement: Структурированная MCP-ошибка отсутствия аккаунта

При отсутствии заведённого аккаунта для переданных `provider` + `login` (или несовпадении `provider`) тул `mail.connect` SHALL вернуть MCP-результат с признаком `isError: true` и текстовым блоком `content[0].text`, содержащим JSON-объект с полями: `error` (код — `account_not_found` или `provider_mismatch`), `message`, `login`, `provider`, `hint` (подсказка о заведении аккаунта через локальный CLI). Ошибка SHALL NOT содержать паролей.

#### Scenario: Ошибка account_not_found возвращает машиночитаемый JSON

- **WHEN** вызов `mail.connect` передаёт `login` и `provider`, для которых нет заведённого аккаунта
- **THEN** MCP-ответ имеет `isError: true`, а `content[0].text` — валидный JSON с `error: "account_not_found"`, полями `login`, `provider` и `hint`

#### Scenario: Ошибка provider_mismatch возвращает машиночитаемый JSON

- **WHEN** вызов `mail.connect` передаёт `login` с заведённым аккаунтом и несовпадающий `provider`
- **THEN** MCP-ответ имеет `isError: true`, а `content[0].text` — валидный JSON с `error: "provider_mismatch"` и полями `login`, `provider`, `hint`

#### Scenario: Ошибка отсутствия аккаунта не раскрывает пароли

- **WHEN** система возвращает структурированную ошибку отсутствия аккаунта
- **THEN** текст ошибки не содержит пароля ни одного заведённого аккаунта

### Requirement: Стратегии аутентификации

Система SHALL поддерживать стратегии аутентификации `basic` (логин + пароль) и `oauth2` (OAuth2 access token по SASL XOAUTH2), выбираемые per-аккаунт через конфигурацию. Архитектура SHALL допускать добавление новой стратегии без изменения логики подключения. Для провайдера `mail` (Mail.ru Group) SHALL применяться стратегия `basic` (логин + пароль приложения); стратегия `oauth2` для Mail.ru SHALL отвергаться как неподдерживаемая.

#### Scenario: Стратегия basic

- **WHEN** у аккаунта `authStrategy` равно `basic`
- **THEN** система авторизуется логином и паролем из конфигурации аккаунта

#### Scenario: Стратегия oauth2

- **WHEN** у аккаунта `authStrategy` равно `oauth2`
- **THEN** система авторизуется access token через механизм XOAUTH2

#### Scenario: Неподдерживаемая стратегия

- **WHEN** у аккаунта `authStrategy` не равен `basic` или `oauth2`
- **THEN** система возвращает ошибку конфигурации и не пытается подключиться

#### Scenario: oauth2 для Mail.ru — неподдерживаемая стратегия

- **WHEN** аккаунт с `provider: "mail"` имеет `authStrategy: "oauth2"`
- **THEN** система возвращает ошибку конфигурации (Mail.ru не поддерживает OAuth2 для IMAP) и не пытается подключиться

### Requirement: Автоопределение стратегии для Outlook

Для Outlook-аккаунта система SHALL проверять работоспособность basic-auth и при отказе SHALL переходить к OAuth2 device code flow для Microsoft identity platform v2.0.

#### Scenario: Basic-auth работает для Outlook

- **WHEN** проверочный запрос basic-auth к `outlook.office365.com:993` успешен
- **THEN** система использует стратегию `basic` для данного аккаунта

#### Scenario: Basic-auth отклонён для Outlook

- **WHEN** проверочный запрос basic-auth отклонён сервером
- **THEN** система инициирует OAuth2 device code flow и использует стратегию `oauth2`

### Requirement: OAuth2 device code flow для Microsoft

При стратегии `oauth2` для Outlook система SHALL выполнять device code flow против Microsoft identity platform v2.0: запрашивать device code, предъявлять пользователю URL авторизации и user code, обменивать код на access + refresh token.

#### Scenario: Инициация device code flow

- **WHEN** запускается OAuth2 для Outlook-аккаунта без действительного токена
- **THEN** система выводит URL `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/devicecode` и user code, ожидая завершения авторизации пользователем

#### Scenario: Пользователь завершил авторизацию

- **WHEN** пользователь вводит user code и завершает вход в браузере
- **THEN** система получает access token и refresh token и выполняет подключение по IMAP

#### Scenario: Истёкший device code

- **WHEN** пользователь не завершил авторизацию до истечения срока device code
- **THEN** система возвращает ошибку с предложением повторить flow

#### Scenario: Отказ пользователя

- **WHEN** пользователь отменяет авторизацию в браузере
- **THEN** система возвращает ошибку и не подключается

### Requirement: Хранение и обновление OAuth2-токенов

Система SHALL сохранять refresh token (и метаданные срока действия) в локальном хранилище вне git и SHALL использовать его для получения новых access token без повторной интерактивной авторизации.

#### Scenario: Обновление access token

- **WHEN** access token истёк, но refresh token действителен
- **THEN** система получает новый access token через refresh token и повторяет операцию без участия пользователя

#### Scenario: Refresh token отсутствует или отозван

- **WHEN** refresh token отсутствует в хранилище или отклонён Microsoft
- **THEN** система инициирует новый device code flow

### Requirement: Жизненный цикл IMAP-сессии

Система SHALL управлять жизненным циклом IMAP-сессии: открытие при подключении, корректное закрытие с освобождением ресурсов, защита от утечек соединений. Система SHALL обнаруживать, что ранее открытая сессия стала непригодной (сервер закрыл простаивающее соединение по IDLE-таймауту, сетевой обрыв), и прозрачно переподключать её при следующем использовании, не требуя от вызывающей стороны повторного `mail.connect`.

#### Scenario: Подключение открывает сессию

- **WHEN** подключение успешно
- **THEN** система держит активную IMAP-сессию, доступную для последующих операций

#### Scenario: Закрытие освобождает соединение

- **WHEN** запрашивается закрытие подключения
- **THEN** система корректно закрывает IMAP-сессию и освобождает сетевое соединение

#### Scenario: Повторное подключение после закрытия

- **WHEN** сессия была закрыта и запрашивается новое подключение того же аккаунта
- **THEN** система устанавливает новую сессию без ошибок

#### Scenario: Ошибка операции не оставляет висящее соединение

- **WHEN** операция завершается ошибкой
- **THEN** система закрывает сессию или возвращает её в пригодное состояние, не оставляя висящее соединение

#### Scenario: Мёртвая сессия в хранилище — прозрачное переподключение

- **WHEN** сессия аккаунта числится в хранилище активных сессий, но реальное TCP-соединение разорвано (сервер закрыл по IDLE-таймауту или сетевой обрыв), и запрашивается операция с этим аккаунтом
- **THEN** система определяет сессию как непригодную и прозрачно переподключает её (закрытие старого client + новое подключение с теми же учётными данными) перед выполнением операции, не требуя повторного `mail.connect` от вызывающей стороны

### Requirement: Проверка живости и прозрачное переподключение

Провайдер IMAP-сессии SHALL предоставлять возможность проверить пригодность соединения без выполнения операции: `isConnectionUsable()` возвращает `true` только если клиент инициирован и нижележащее соединение пригодно (imapflow `client.usable === true`), иначе `false` (включая состояние `client === null` после неудачного/невыполненного переподключения). Провайдер SHALL предоставлять `reconnect()` — прозрачное переподключение: закрытие старого client и новое подключение через существующий lifecycle, без изменения учётных данных аккаунта. `reconnect()` SHALL быть доступен для вызова внешними потребителями (guided-команды CLI, хранилище сессий), чтобы поднять упавшее соединение до выполнения операции.

#### Scenario: Пригодное соединение — isConnectionUsable=true

- **WHEN** сессия открыта и соединение активно
- **THEN** `isConnectionUsable()` возвращает `true`

#### Scenario: Разорванное соединение — isConnectionUsable=false

- **WHEN** сервер закрыл соединение (IDLE-таймаут) или сетевой обрыв разорвал сокет, а сессия числится активной
- **THEN** `isConnectionUsable()` возвращает `false` (imapflow `client.usable === false`)

#### Scenario: client=null после неудачного reconnect — isConnectionUsable=false

- **WHEN** переподключение обнулило client и не завершилось новым подключением
- **THEN** `isConnectionUsable()` возвращает `false` (толерантен к `client === null`)

#### Scenario: Прозрачное переподключение поднимает соединение

- **WHEN** вызывается `reconnect()` на сессии с разорванным соединением
- **THEN** провайдер закрывает старый client и открывает новый с теми же учётными данными; после успеха `isConnectionUsable()` возвращает `true`

#### Scenario: reconnect сохраняет учётные данные

- **WHEN** выполняется `reconnect()`
- **THEN** учётные данные аккаунта (логин, пароль приложения, OAuth2-стратегия) остаются неизменными — меняется только транспортное соединение

### Requirement: Список папок ящика

После успешного подключения система SHALL возвращать список папок ящика: имя, разделитель пути, флаги (включая `\Inbox`, `\Sent`, `\Drafts`).

#### Scenario: Список папок возвращён

- **WHEN** запрашивается список папок при активном подключении
- **THEN** система возвращает непустой список, содержащий папку «Входящие» (`\Inbox`)

#### Scenario: Запрос папок без подключения

- **WHEN** запрашивается список папок без активного подключения
- **THEN** система возвращает ошибку с указанием, что подключение не установлено

### Requirement: Безопасное хранение учётных данных

Система SHALL хранить пароли приложений и OAuth2-токены только в локальных файлах вне git (`.env` для паролей, отдельный token store для OAuth2-токенов). Система SHALL NOT логировать секреты или выводить их в сообщения об ошибках.

#### Scenario: Token store вне git

- **WHEN** создаётся файл хранилища OAuth2-токенов
- **THEN** путь хранилища добавлен в `.gitignore` и не отслеживается git

#### Scenario: Секреты не попадают в логи

- **WHEN** происходит ошибка аутентификации или подключения
- **THEN** сообщение об ошибке не содержит пароля, access token или refresh token
