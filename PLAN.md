# План разработки: Email Helper Agent

> Статус: v1.0 — решения по уточняющим вопросам зафиксированы 2026-10-27.
> Файл с тестовыми аккаунтами `agent-accounts.txt` добавлен в `.gitignore`.
> Секреты хранятся локально и в `.env`.
>
> ⚠️ Технический риск по Outlook (см. раздел 3.1) — требует проверки при старте Фазы 1.

## 1. Назначение продукта

Агент-помощник для работы с электронной почтой (Яндекс Почта, Outlook.com).
Архитектура «оркестратор + субагенты»: дорогая модель анализирует письма,
дешёвая модель выполняет рутинные действия (скачивание вложений, отправка писем).

### 3.0 Технический риск по Outlook (требует проверки в Фазе 1)

Microsoft отключила **базовую аутентификацию** (логин+пароль) для IMAP/POP/SMTP
в Exchange Online (корпоративные M365-аккаунты) — Basic Auth больше не работает,
нужен OAuth 2.0 по протоколам POP3/IMAP/SMTP.

Для **личных** `@outlook.com`-аккаунтов статус неоднозначен: часть личных ящиков
продолжает принимать логин+пароль по IMAP, часть переведена на OAuth. Аккаунт в
`agent-accounts.txt` — личный (`@outlook.com`), но пароль в файле может оказаться
**обычным паролем учётки** (а не «паролем приложения»). Поэтому:

1. В начале Фазы 1 — проверочный тест подключения к `outlook.office365.com:993`
   с логином/паролем из файла.
2. Если basic auth не работает — реализовать OAuth2 (device code flow или
   authorization code) для Microsoft identity platform v2.0.
3. Архитектура провайдера делается так, чтобы аутентификация была **плаваемой**
   (стратегия `basic` | `oauth2`), добавляется прозрачно, без переписывания логики.
4. Для Яндекс Почты basic auth (пароль приложения) работает стабильно —
   аутентификация `basic`, `imap.yandex.ru:993`, `smtp.yandex.ru:465`.

### 3.1 Роли агентов

- **Оркестратор** (glm-5.2): принимает запрос пользователя, разбирает интент,
  планирует последовательность действий, делегирует субагентам, собирает
  итоговый ответ. Держит контекст диалога.
- **Субагент-анализатор** (glm-5.2): глубокий анализ содержимого писем,
  саммари по одному/нескольким письмам, извлечение сущностей, классификация
  тематики. Работает с дорогой моделью.
- **Субагент-помощник** (glm-5.3-flash, дешёвая): рутинные операции —
  подключение к почте, поиск писем по критериям, скачивание вложений,
  отправка писем, работа с папками, индексация в векторную БД.

### 3.2 Ключевые тулы (tools)

| Тул | Назначение | Субагент |
|-----|-----------|----------|
| `mail.connect` | Подключение к ящику (IMAP) | помощник |
| `mail.listFolders` | Список папок ящика | помощник |
| `mail.search` | Поиск писем по критериям (дата, тема, отправитель, папка, входящие/исходящие) | помощник |
| `mail.fetch` | Получение тела + заголовков письма | помощник |
| `mail.downloadAttachments` | Скачивание вложений в локальную папку | помощник |
| `mail.send` | Отправка письма (SMTP) по критериям | помощник |
| `mail.analyze` | Анализ содержимого письма(ий), саммари | анализатор |
| `embeddings.index` | Индексация письма в FalkorDB (вектор + метаданные) | помощник |
| `vector.search` | Семантический поиск писем по векторной близости | помощник |
| `filesystem.ensureDir` | Создание целевых папок для вложений | помощник |

## 5. Фазы разработки

Каждая фаза реализуется по SDD: спека → дизайн → задачи → реализация → тесты → archive.
Между фазами — контрольная точка (демо + ревью спек).

---

### Фаза 0 — Фундамент проекта (без LLM, без почты)
**Цель:** пустой рабочий проект, готовый к SDD-разработке.

- Инициализация git-репозитория, `.gitignore`, `README.md`.
- `package.json` (ESM, type:module), `tsconfig.json` (strict), Node 20.
- Vitest, ESLint, Prettier.
- Установка OpenSpec CLI: `npm i -g @fission-ai/openspec@latest`, `openspec init`.
- `agent.md` (черновой), структура `skills/` и `openspec/`.
- `docker/docker-compose.yml` с FalkorDB (прод-образ + persistence + пароль).
- `src/config/schema.ts` (zod): аккаунты почт, ключ RouterAI, путь к папкам.
- `.env.example`.
- Проверка: `docker compose up -d` поднимает FalkorDB; `npm test` зелёный; `openspec validate` проходит.

**SDD-изменение:** `bootstrap-project` (capability: `project-skeleton`).

---

### Фаза 1 — Базовая работа с почтой (IMAP/SMTP, без LLM)
**Цель:** подключение, поиск, чтение, скачивание вложений для Яндекс + Outlook.

- Абстракция `MailProvider` (интерфейс) + реализации Yandex/Outlook.
- **Проверочный тест Outlook basic-auth** (см. риск 3.0) — первой задачей фазы.
- Подключение по IMAP (imapflow): Яндекс с паролем приложения; Outlook — basic или OAuth2 по итогам проверки.
- Подключение по IMAP (imapflow) с паролем приложения.
- `mail.listFolders`, `mail.search` (дата, тема, отправитель, папка, направление).
- `mail.fetch` (заголовки + тело + метаданные вложений).
- `mail.downloadAttachments` (в заданную локальную папку, безопасные имена).
- Поддержка входящих/исходящих/произвольной папки.
- Юнит-тесты с моком IMAP-сервера; интеграционный тест против тестового ящика (опц.).
- Безопасное хранение учётных данных (пароли приложений в .env / зашифрованном store).

**SDD-изменения:** `mail-connect`, `mail-search`, `mail-attachments` (capabilities: `mail/connection`, `mail/search`, `mail/attachments`).

---

### Фаза 2 — LLM-интеграция и агентная оркестрация
**Цель:** оркестратор + субагенты через RouterAI, анализ писем.

- `llm/routerai-client.ts` (OpenAI-совместимый, supports tools/function calling).
- `llm/models.ts`: glm-5.2 (оркестратор+анализатор), glm-5.3-flash (помощник).
- Каркас агентов: цикл tool-calling, обработка tool-вызовов, контекст диалога.
- `skills/*.md` — системные промпты ролей.
- `mail.analyze` (анализатор): саммари одного письма / нескольких, извлечение ключевых тем.
- Оркестратор: разбор интента пользователя → план → делегирование → сбор ответа.
- Тесты: мок RouterAI (фикстуры ответов), проверка маршрутизации задач.

**SDD-изменения:** `llm-client`, `orchestrator`, `analyzer-agent`, `helper-agent` (capabilities: `llm/routerai`, `agent/orchestrator`, `agent/analyzer`, `agent/helper`).

---

### Фаза 3 — Векторное хранилище и семантический поиск
**Цель:** индексация писем в FalkorDB, поиск по смыслу.

- Клиент FalkorDB (`falkordb` npm), соединение из Docker.
- Графовая модель: узел `Email` (id, тема, дата, отправитель, папка) + связь к `Account`/`Folder`.
- Векторный индекс над embedding тела/темы письма.
- `embeddings.index` (RouterAI embeddings через bge-m3).
- `vector.search` — семантический поиск писем.
- Гибридный поиск: критерии (фильтры) + векторная близость.
- Тесты с встроенным/тестовым FalkorDB.

**SDD-изменения:** `vector-store`, `semantic-search` (capabilities: `storage/falkor`, `mail/semantic-search`).

---

### Фаза 4 — Отправка писем по строгим критериям
**Цель:** `mail.send` по SMTP, шаблоны, валидация критериев.

- SMTP-клиент (nodemailer) для Яндекс + Outlook.
- Схема «критериев письма»: получатели, тема, тело, вложения, кодировка.
- Поддержка нескольких получателей (TO/CC/BCC).
- Валидация и предпросмотр перед отправкой (подтверждение пользователем).
- Тесты с мок SMTP-сервером (smtp-server npm в тестах).

**SDD-изменение:** `mail-send` (capability: `mail/send`).

---

### Фаза 5 — CLI/Terminal интерфейс
**Цель:** интерактивная работа с агентом из терминала.

- REPL/чат в терминале (ввод запроса → ответ агента с tool-вызовами).
- Команды: подключить аккаунт, искать письма, скачать вложения, проанализировать, отправить.
- Вывод прогресса tool-вызовов, форматированные отчёты.
- Тесты интерфейсных функций (мок ввода/вывода).

**SDD-изменение:** `cli-transport` (capability: `transport/cli`).

---

### Фаза 6 — MCP-сервер
**Цель:** экспонирование тулов агента по Model Context Protocol.

- MCP-сервер над реестром тулов (`@modelcontextprotocol/sdk`).
- Регистрация тулов с JSON-схемами параметров.
- Возможность подключения внешних клиентов (в т.ч. pi/Claude/другие LLM).
- Аутентификация/изоляция учётных данных.
- Тесты контрактные (вызов тулов через MCP-клиент в тестах).

**SDD-изменение:** `mcp-server` (capability: `transport/mcp`).

---

### Фаза 7 — Telegram-бот
**Цель:** доступ к агенту через Telegram.

- Telegram Bot API (telegraf/grammy).
- Привязка Telegram-пользователя → конфиг аккаунта почты.
- Команды + свободный текст → оркестратор.
- Безопасное хранение токена бота и учётных данных.
- Тесты с моком Telegram API.

**SDD-изменение:** `telegram-transport` (capability: `transport/telegram`).

---

### Фаза 8 — Полировка, документация, E2E
**Цель:** готовность к использованию.

- E2E-сценарии (поиск→анализ→скачивание→ответ; отправка письма).
- Документация: README, `agent.md` финал, user-guide.
- Observability: логирование tool-вызовов, расходы токенов.
- Безопасность: аудит хранения секретов, ограничение доступа.
- Покрытие тестами ≥ целевого порога.

**SDD-изменение:** `hardening-docs` (capability: `ops/observability`).

## 8. Зафиксированные решения (по ответам пользователя 2026-10-27)

### 8.1. Модели и RouterAI

- **Основная модель:** `z-ai/glm-5.2` (оркестратор + анализатор).
- **Дешёвая модель:** `z-ai/glm-5.3-flash` (субагент-помощник).
- **Embeddings-модель:** `baai/bge-m3` (мультиязычная, для русскоязычных писем).
- **API-ключ RouterAI:** хранить в `.env`.

### 8.2. Почтовые аккаунты и доступ

- **Тип аккаунтов:** личные.
- **Провайдеры:** Яндекс Почта + Outlook.com (вместо Mail.ru по решению пользователя).
- **Тестовые ящики:** в файле `agent-accounts.txt` (логины `@yandex.com` и `@outlook.com`).
  Файл добавлен в `.gitignore`, в git не попадает.
- **Риск по Outlook (basic auth):** см. раздел 3.0 — проверяется в начале Фазы 1.

### 8.3. Хранение учётных данных

- **Хранение:** `.env` (простой вариант, как выбрал пользователь).
- `.env.example` содержит названия переменных без значений.
- `agent-accounts.txt` игнорируется git и используется как источник для ручного переноса в `.env`.

### 8.4. Векторная БД и данные

- **Объём писем:** сотни на ящик → индексация полная (по требованию или при подключении).
- **Что индексируем:** тема + тело (текст). Вложения-документы — отдельная фича (после Фазы 3).
- **FalkorDB:** локально через docker-compose, персистентность в volume.

### 8.5. Отправка писем

- **«Строгие критерии» письма:** получатели (TO/CC/BCC), тема, текст, необязательные вложения, кодировка.
- **Подтверждение перед отправкой:** да — агент показывает черновик и ждёт подтверждения пользователя.

### 8.6. Транспорты и окружение

- **Порядок:** CLI (Фаза 5) → MCP (6) → Telegram (7).
- **Telegram-токен:** пользователь создаст позже через @BotFather. До этого Фаза 7 на паузе; MVP — CLI.
- **ОС:** Linux, деплой Linux/Docker.

### 8.7. Процесс разработки

- **Язык документации:** русский (`agent.md`, `skills/`, спеки, README).
- **Размер спек:** дробить фазы на несколько мелких SDD-изменений (как в разделе 5).
- **Старт:** после согласования скорректированного плана — Фаза 0.
